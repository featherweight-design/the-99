254 set codes in a dropdown is not a filter

Today the Set ▾ control on filter-bar.tsx is a native <select> of 254 raw lowercase codes — blb, clb, afr — in whatever order the query returned them. This addendum replaces that one control with a searchable, multi-select panel: set names, owned-sets only, a card count per set, newest first. Nothing else on the shipped surface is redesigned — the bar, the chip row and the list are reused as-is. Every state below leads with the phone, desktop beside it.

Form factor
Anchored popover under the trigger on desktop; bottom sheet under 768px. Same panel, two mounts.
Selection
Multi-select, applied live on every toggle. No Apply button — the list behind you is the preview.
Order
Release date, newest first (locked). Ties broken A→Z by name. Selected sets pin to the top on open only.
Counts
Owned cards per set, respecting the other active filters. A set that reaches 0 stays listed, dimmed and unselectable.
Siblings
Type ▾ converts to the same panel with search off. Sort ▾ becomes a single-select menu, never a listbox.
A11y model
Combobox + multi-selectable listbox, aria-activedescendant. Focus never leaves the search field.

Why not keep the native select
A native <select> cannot show a count beside an option, cannot be searched on iOS, cannot hold more than one value without becoming a scrolling multi-list nobody can operate on a phone, and renders 254 rows of blb in OS chrome that ignores the brand entirely. Four of the spec's locked decisions are impossible inside it. That is the whole justification for a custom widget — and the reason the keyboard and screen-reader model below is specced as tightly as the pixels.
Where the selection lives
In the shipped chip row, unchanged — one dismissable chip per set, beside the colour and type chips. The trigger only counts; the chips carry the names, and Clear all already clears them.

Keyboard & screen reader
TAB
Reaches the trigger — one stop, between Type and Sort, exactly where the <select> sat.
↵ / ␣ / ↓
Opens the panel and moves focus into the search field. ↓ also marks the first option active.
↑ ↓
Move the active option and scroll it into view. DOM focus stays in the input — the active row is named by aria-activedescendant, so typing never breaks. No wrap at the ends.
␣ / ↵
Toggles the active option. The panel stays open and the query is kept — picking three sets from one search is the common act. Disabled (0-count) rows don't toggle.
ESC
Closes and returns focus to the trigger. Selections are already applied, so there is nothing to cancel — Esc is dismiss, never undo.
TAB ⇥
Desktop: moves to Clear, then out — closing the popover. Mobile: focus is trapped in the sheet (aria-modal) and cycles search → rows → Clear → Done.

The toggle announcement is the same live region the chip row already writes to — one region for the whole filter bar, so two filters changed in quick succession read once, in order, not on top of each other. Scope discipline
The Set panel is the ticket. Type and Sort are drawn here so engineering can see the row's end state and build the panel general enough to serve all three — but they are follow-up work, not this change. Shipping Set alone leaves two native selects in the row for a release; that is acceptable and expected.

The Color control is not converted at all: five WUBRG pips, already custom, already good. It never becomes a panel.
