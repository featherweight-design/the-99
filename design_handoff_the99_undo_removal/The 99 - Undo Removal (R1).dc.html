R1
Undo a removal · one control, three labels

The row does not leave.

Today the only reversal for a removal is Discard, which reverts the whole draft behind a confirm. Pull is not the other end of it — that pulls a card from another deck, and it is an acquisition, not a reversal. So removing one card by mistake costs either the mistake or every other change in the draft.

The answer is one mutation in two positions, at one weight — a light brass Undo link on the struck row in the decklist at the moment of the cut, and Put back on every row under Going out · 17 for as long as the draft exists. Two words because the two clocks are two different promises: at the moment of the tap no other deck can have taken the copy, so it genuinely is an undo; a week later it is a request that can be refused. Optimistic, so there is no in-flight state at all — it applies on tap and the server is heard from only if it refuses. No toast, no bar, no shortcut, no new storage, and no new left rule.

Read README.md for the three answers and the decisions log, STATES-restore.md for the state matrix, copy strings for production copy including the one shipped string this feature must edit, and READINESS.md for what blocks a green.

The three questions, answered before the frames
1 · Is Going out the whole answer?
No — but it is the durable half, and it needs no new surface. Two things stop it being the whole answer. The cut happens on the deck page, and §Decisions 2 says removes are never drawn there — so the row vanishes and the evidence lives one route away, with nothing on screen saying a reversal exists. And a restore re-asserts a claim, so it decays: the longer between cut and restore, the likelier another deck has taken the copy. A path that only exists a route away is a path whose commonest outcome, over time, is refusal.
2 · What carries it at the moment?
The row you just cut stays exactly where it was, struck through, with a brass Undo link in the slot the remove control occupied. A link and not a button, and one word: at the moment of the tap no time has passed, so it genuinely is an undo and the row can stay 40px and one line. Not a transient bar — the product owns no toast and every handoff in this feature has refused one. The struck row is not a ghost of an inventory of removals (which is what §Decisions 2 rejected at seventeen rows); it is the trace of your tap, so it exists only where the tap happened and only for the cuts you made by hand.
3 · How long does it live?
Two clocks, because they are two different things. The struck row is a visit — a gesture trace, gone on navigation, because persisting it would mean storing a row that is not in the draft, which is versioning the draft. The Going out restore lives until commit, and costs nothing: it is derived from draftDiff.removes, which already enumerates every cut. Nothing expires — only the shortcut does, which is why no surface warns about a window.
The unusual constraint, taken first — a restore can be refused
Putting a card back re-asserts a claim another deck may have taken while it was out, and the server re-reads every claim and refuses with a named reason exactly as pullFromDeck does. So this is not an undo — an undo is a promise, and this control cannot make one. It is a request, and the design draws the refusal as a first-class state rather than an error path.
And a refused restore is not a dead end — it re-prices. Decline the pull and the card still comes back, carrying its price: the card still goes back in your deck; what it lost is its free copy. So the refused row takes the guard family's own vocabulary — a mono tag naming the condition beside the deck that now holds it, in BuyTag's shape, with the action that actually applies in Put back's slot at the same geometry. That is deckVersioningCopy.pullGuard*'s shape with a third and fourth tag word, not a fifth construct: claimed (a route exists — pull it or buy it) and commander (no route exists, so no control).
One treatment, three labels
All three row controls are now borderless brass links at one weight — Undo in the decklist, Put back and Pull under Going out. One treatment, three labels, no buttons in any row. The words still differ, because the promise does.
No fourth left rule
Versioning's gap 11 warned that a fourth use of the left rule makes it a colour code with no key. The strikethrough is the marker — not a hue, and the live control beside it says the word.
It spends less than it takes
The link takes the slot the remove control just occupied — the cursor is already there — and the struck row drops its $ tile, because a row that is not in the deck is not asking for money. 34px in, 22px out, and no note: the name is wider than on a plain row.
Nothing reflows
The real failure of a vanishing row at 101 rows is not that the evidence is gone — it is that everything below it moved. The struck row extends the matrix's rule 4, nothing unmounts mid-write, by one beat.
A paste leaves no struck rows
Seventeen strikethroughs from a Deckcheck paste is precisely what §Decisions 2 refused, and it still is. The struck row is scoped to hand cuts in this visit. Paste removals are restorable only under Going out.
The banner gets nothing
The ≤6 inline name lines are a statement, not rows, and the banner already carries three controls. A fourth on each of six lines is a control grid in a box whose job is the count and the money. review changes is one tap.

There is one kind of struck row, which is why there is no note. A card added in this draft and then cut is not a removal — it is an un-add: it was never in v2, so nothing went out, and the draft simply has no opinion about it any more. No row, no strikethrough, and nothing under Going out, because it is not going out of anything. draftDiff files it as no change, which it already does. The way back is to add the card again, which is what the deck page is for.
That deletion is the simplification, and it removes a rule rather than a label. R1 drew two struck-row variants with a mono note distinguishing them, because they restored to different row states — a plain row or a pending add. But the player does not need that before the tap; they see the result. So the second variant is gone, the note is gone, and with them the “a restore returns the row to whatever it was” rule, one state in the matrix, one copy string, and the widest thing on the row.
The accessible name carries the word. {name}, cut from this draft, and the control's own name is Undo cutting {name} — the row supplies the card, so the visible label does not have to. The strikethrough is a locator, the same standing the brass rule has.
Focus lands on the control, not the row. After a removal, focus moves to Undo — which makes the reversal reachable with one key press without the product owning a keyboard shortcut, and needs nothing on mobile, where the thumb is already on that slot.

Rejected, and why

four candidates for question 2
Rejected · a transient bar
The product owns no toast, tray or snackbar, and three handoffs have refused one — including versioning's own discard ruling, which turned down an undo window for exactly this reason. A bar would also be the only element in the feature with a deadline, and a deadline on a claim-checked request is a promise the server has not made. At 101 rows it would also cover the list it is talking about.
Rejected · a left rule on the struck row
Brass already means pending add and warning means we cannot name this. Versioning's gap 11 said plainly that a fourth use turns the left rule into a colour code with no key, and this is the fourth use. Strikethrough is not a hue, needs no key, and survives the “words, never colour alone” floor on its own.
Rejected · a per-row toggle, like the update preview's Keep
A toggle says the removal has not happened yet. It has — the draft is already short a card and every counter on the page has moved. A checkbox that reverses a committed-to-the-draft fact is a control pretending to be a form field, and it cannot represent a refusal at all: there is no “off” state for we tried and another deck has it.
Rejected · a stack of recent cuts above the list
It is Going out · 17 again, drawn a second time on the surface that has the least room, and it puts the cut card in a place it has never been. The row's own position is the strongest possible locator — you know where you just tapped.

The justification is specific to this action, not a general preference. Every other write in the feature — commit, discard, a pull — is a decision, and a decision deserves to be seen landing. The refusal is rare, and it is cheap to state when it comes.
It is a deliberate departure from the matrix's rule 4, nothing unmounts mid-write. Under Going out the row does unmount before the server has answered. That rule exists so a player is never left unsure whether a write landed — and here the revert is visible, named and returns the row to the position it left (alphabetical inside its type group), so the uncertainty the rule protects against does not arise. Notes for engineering
One mutation, restoreRemovedCard(deckId, oracleId), and it is a claim write. It re-asserts the deck's claim inside a transaction that re-reads every competing claim, refuses with a named reason, and revalidates through revalidateClaims(deckId, userId) — not deckSurfaces(), for the reason a pull already needs it. Refusal reasons are an enum, not a string: claimed_by_deck and is_commander_of, each carrying the deck.
It restores, it does not add. A restored card keeps the seniority its claim had — which is also why review.outNote could not stay as written, since it asserted that putting one back is adding it.
It is optimistic, and the client owns the revert. Apply locally on tap, fire the mutation, and on a named refusal put the row back where it was — struck in the decklist, or re-inserted into Going out at its alphabetical position inside its type group, with every figure returned to its previous value. No spinner, no disabled state, no in-flight label, and no toast: the refusal is a sentence in the row it is about. Every other write in the feature still settles the ordinary way — this one is optimistic because it is the correction of a mistake rather than a decision.
An un-add is not a removal, and must not become one. Cutting a card this draft added returns the draft to no change on that card: draftDiff files it as nothing, so there is no struck row, no row under Going out, and no restore affordance anywhere. If it lands in removes instead, the review page grows a row asserting a card left a version it was never in — the same class of defect as the unfiltered basics in the pull list.
No new storage, and specifically no draft-of-the-draft. Going out is draftDiff.removes, which already enumerates every cut; the struck row is client state in the decklist component, keyed by oracle id, dropped on unmount. Nothing here is the is_draft column §Data model refused, and nothing survives a reload that is not derived.
The commander refusal must be in the availability payload, the claim refusal must not be. State 05 is drawn without a control, so the client needs to know it before the tap — the same per-row flag the pull guard already needs, read for the removes side too. State 04 is the opposite: it is discovered on submit, by design, because pre-flighting it would mean polling every cut card's claims for the life of the draft.
The struck row is scoped to hand cuts. The removal path that draws it is the decklist's own remove control. A Deckcheck paste, a re-import and a bulk operation draw nothing — if the flag is set on the diff rather than the gesture, seventeen strikethroughs appear and §Decisions 2 is broken by the back door.
Focus after each settle is named. After a removal, the row's Undo; after a restore in the decklist, the restored row; after a restore under Going out the row leaves, so focus goes to the group heading it left, never to the next row's control — which would put a live restore under a finger that just used one. On a revert, focus follows the row back.
One live-region message per settle, on the existing region. Necrotic Ooze is back in the deck. 101 cards, 16 going out. On a refusal, the named reason once. No motion anywhere — no fade on the strikethrough, no collapse on the leaving row, no count-up. A row that animates out of a list is a row you cannot find again if you were wrong twice.
One shipped string is edited and it is deckVersioningCopy.review.outNote. Its second clause is this feature's own argument against itself. Nothing else in deck-versioning.ts changes; the new strings are a restore block in the same file, not a new one.
Money moves in exactly one case, and it is the refusal. A restore that succeeds changes no money.
