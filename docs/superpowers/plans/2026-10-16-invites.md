## The model

### Tables (one migration, `0140_invites`, in PR 1)

- **`invite_balances`**: `user_id` (pk), `held` (int, `>= 0`), `updated_at`. The stock, counting what is left AND
  what is holding. Only an admin write raises or sets it; only a spend lowers it, by one.
- **`invite_reservations`**: one row per invite a sender put in motion.
  - `id` (uuid, pk; the `publicMetadata.inviteReservation` value), `user_id` (the SENDER; named `user_id` because
    `purgeAccount` deletes every `PURGE_ORDER` table by that column), `kind` (`email` | `qr`).
  - `state`: `qr_open` → `claimed` → `spent`, or `reserved` → `spent`; either ends `returned` or `revoked` instead.
    `spent`, `returned` and `revoked` are final. A check ties each state to the columns it needs.
  - `qr_token_hash` (sha256 of the token, unique, `qr` only), `qr_expires_at` (created + 15 minutes). The token is
    DERIVED, never stored: `base64url(HMAC-SHA256(INVITE_CODE_SECRET, "qr-token:" || id))`, 256 bits, with a label of
    its own so it never collides with the code's HMAC. So the server can re-show a live QR from a fresh page or another
    device (R3) by recomputing it, while a database read alone cannot.
  - `holds_until`: the reservation's own clock, set to now + 7 days when the email is sent or the QR is claimed.
  - `email` (nullable; erased on every final state), `clerk_invitation_id` (nullable).
  - The claim (`qr` only): `claim_secret_hash` (the newcomer's browser binding, an httpOnly cookie), `code_hmac`,
    `code_expires_at`, `code_sent_at`, `code_tries`, `proven_at`.
  - `created_at`, `resolved_at`. Index `(user_id, state)`.
- **`invite_edges`**: the tree. `id` (pk), `inviter_user_id` (nullable), `invitee_user_id` (nullable, unique where not
  null), `kind` (`email` | `qr`), `joined_at`, `receipt_shown_at` (nullable: whether the newcomer has been shown the
  receipt band, kept apart from the spend so the two orders below draw the same). A founder is an account with no edge as invitee.

### What "held" means, computed in one place

`src/lib/invites/rules.ts` (pure) owns it, so every count line, the server gate and /admin read one definition:

- A row HOLDS an invite when it is `qr_open` and `qr_expires_at > now`, or `claimed`/`reserved` and
  `holds_until > now`.
- **Left** = `held` − rows holding. **Out** = left ≤ 0. The line's parts (`waiting`, `heldByQr`, `heldByThisQr`) come
  from the same rows.
- Expiry is DERIVED from time, so a count is right whether or not the sweep has run. The sweep only makes the row
  say what time already decided (state `returned`, email erased, Clerk invitation revoked).

Every write that spends, holds or sets takes the sender's lock, `pg_advisory_xact_lock(hashtext('invites:' || sender))`,
and re-reads left under it, so two presses cannot both take the last invite.

**The invariant: `held` ≥ the rows holding**, always, so a spend can never drive `held` below zero and roll back a
friendship. A hold needs left ≥ 1 (so `held` > holding before it); a spend removes one holding row and one from `held`
together; a spend of a row no longer holding is refused before `held` moves; and an admin Set of N writes
`held = N + holding` under the same lock, never a bare N. `probe:invites` asserts it after every write.

### The sender's two ways

**By email** (`sendEmailInvite`, PR 2). Shape-check the address (no server call on E1). Under the lock: refuse `out`;
insert a `reserved` row with `holds_until` = now + 7 days and the address; commit. Then call Clerk
`createInvitation({ emailAddress, notify: true, expiresInDays: 7, redirectUrl, publicMetadata: { inviteReservation } })`
WITHOUT `ignoreExisting`; `redirectUrl` as below. A 4xx refusal is caught and logged by kind, never by address, and the reservation stands as
if it had succeeded. A transport failure (Clerk unreachable, a timeout or a 5xx) is
INDETERMINATE: Clerk may have created and mailed the invitation before its answer was lost, so the reservation is never
released for it. It stands, holds like any other, and is answered as a success; the sweep reconciles it (below). E6's
toast is kept for a failure before the reservation commits (our own database, or the action never reaching the
server), the one case in which nothing can have been sent. The action
answers after `max(SEND_FLOOR_MS, elapsed)`; `SEND_FLOOR_MS` is set in PR 2 from staging's measured Clerk latency (its
p99 plus a margin) and pinned by a test that both branches wait the same.

**At the table** (`showInviteQr`, PR 2). Under the lock: a live `qr_open` row is returned as it is (R3); otherwise refuse
`out`, insert a `qr_open` row and derive its token. The sheet draws the QR of `/join/<token>`. The sender's sheet turns on
the shipped watch (`use-invite-watch.ts`), extended to read `/api/invite-qr?t=` (signed in, the sender's own row only,
`private, no-store`): `live` with seconds left, `claimed` (Q3, "Invitation sent", at the newcomer's Send code),
`expired` (Q4). Make a new QR is `showInviteQr` again.

### The newcomer (`/join/[token]`, public)

Each step re-reads the row by token hash; the token's sender's switches decide whether the page works
(`resolveSwitchEnv(sender)`: off reads as N12). A row that is not `qr_open`/`claimed`, past its time, or out of tries
draws N11 or N12, which name nobody.

1. **Send code** (`claimInvite`). Shape-check, and refuse with R14's toast BEFORE anything is claimed when Resend is
   not configured (no key, no sender, no `INVITE_CODE_SECRET`), so a misconfigured deployment never holds an invite
   for 7 days and mails nothing. Then, under the sender's lock, a `qr_open` row moves to `claimed` with
   `holds_until` = now + 7 days, the address, a fresh claim secret (set as an httpOnly, `SameSite=Lax`, path-scoped
   cookie) and a code. Then Resend mails the code. The same floor as the email path, whatever the address. A claimed
   row whose cookie matches re-sends on the same claim (Use a different email replaces the address; the 7-day clock
   does not restart, G-8). Resend failing is R14's toast and leaves the claim standing.
2. **Confirm** (`confirmCode`). The cookie must match the claim; the HMAC is compared in constant time; a wrong code
   counts a try, and the fifth wrong try ends the row (`revoked`, its invite returned, N12). A code past 10 minutes is
   N5. The right code sets `proven_at`.
3. **Continue to sign-up** (`handOver`). Only a proven claim, with its cookie. The server looks the address up
   (`users.getUserList({ emailAddress })`): an account draws N9 and the reservation keeps holding until its 7 days, as
   every unspent reservation does. Otherwise it creates the invitation with `notify: false, ignoreExisting: true`,
   `expiresInDays: 7` (as the email path; never Clerk's 30-day default) and the reservation id, stores the invitation id, and redirects to the invitation's `url`. Reopening `/join/<token>` in
   the same browser within the 7 days re-draws N6; Continue then revokes the stored invitation and creates a fresh
   one, so no ticket URL is ever stored.

### Where the ticket lands (PR 3 verifies on staging)

An invitation's `redirectUrl` is where the ticket is TAKEN, not where a finished sign-up lands, so it never names
`/friends`: it is left unset, so the ticket goes to Clerk's hosted sign-up (Account Portal), which consumes it. Where a
finished sign-up lands is the instance's after-sign-up redirect, set to `/friends` on both Clerk instances (Rollout
step 2); it is instance-wide and carries no sender. If the staging walk finds the hosted page does not consume a
ticket with `redirectUrl` unset, `redirectUrl` is set to the hosted sign-up URL itself, and the PR says which.

### The spend (PR 3)

`spendInviteOnSignUp(newUserId, reservationId, name)` in `src/lib/invites/spend.ts`, one transaction: lock the sender,
then the reservation row `for update`; require state `reserved` or `claimed` (a `spent` row whose edge names this
invitee is the idempotent no-op, and a row whose `holds_until` has passed is refused, so an invitation that outlives
its hold by a part-day spends nothing); set `spent`, erase the address; lower `held` by one; insert the edge; and call
one new function in `src/lib/social/`, `welcomeInvitedIn(tx, sender, newcomer, name)`, which ensures the newcomer's
`social_profiles` row (Clerk's first name, else `Player`) and forms the friendship through `befriendIn`. Every read or
write of a social table stays in `src/lib/social/` (`check:social-reads`): the newcomer page's sender card (name and
commander) is likewise read through a new `readInviteSender(senderUserId)` there. A reservation that is
`returned` or `revoked` forms nothing and spends nothing: the newcomer has an account and no friend, which is what a
lapsed invitation means.

It runs from two places, both idempotent, so the order never matters:

- **`user.created`** in `POST /api/clerk-webhook`, a branch beside `user.deleted`, reading
  `data.public_metadata.inviteReservation`. It reads no feature switch: an invitation already accepted is honored
  whatever the switches say, as a taken payment is.
- **The newcomer's first `/friends`**, which may arrive before or after the webhook. When the reader's own
  `publicMetadata.inviteReservation` is set and that reservation is not yet spent, the page runs the spend first. Then,
  in EITHER order, when the reader's edge has `receipt_shown_at` null, it sets it and draws the shipped receipt band
  naming the edge's inviter (the band's `accepted` state, set from the edge rather than from the URL, since the
  after-sign-up redirect carries no sender). So the band draws once, on the first arrival, whether the webhook or the
  page spent the reservation. Public metadata is written only by our backend through the invitation, so the reader
  cannot forge it. `probe:invites` runs both orders (webhook first, page first) and asserts one band, once.

### The sweep (PR 3)

It also RECONCILES an email reservation with no `clerk_invitation_id` (an indeterminate send, above): it lists the
address's pending invitations (`getInvitationList({ query })`) and records the one whose public metadata names this
reservation, or, at return, revokes it. So an invitation Clerk did create is never left usable past its hold, and its
spend still finds the reservation it names.

`GET /api/cron/invite-sweep`, already public through `src/proxy.ts`'s `/api/cron(.*)` and authorized only by
`CRON_SECRET` (the account sweep's rule), hourly in `vercel.json`. It moves every row whose time has passed to `returned`, erases its address and revokes
its Clerk invitation (best effort, logged; a failed revoke is retried next hour while the id is kept). Counts never
wait on it (above).

### Purge (PR 1 writes the rule, PR 3 the Clerk half)

- `invite_balances` and `invite_reservations` (both keyed `user_id`) join `PURGE_ORDER`. The purge collects the reservations'
  `clerk_invitation_id`s inside its transaction and revokes them after commit; a revoke that fails is left to Clerk's
  own 7-day expiry, which is the same lapse.
- `invite_edges`: the deleted side's column is set null at runtime by an `INVITES_UNLINKED` step
  (`src/lib/invites/purge.ts`, called from `purgeAccount` beside `purgeSocialIn`, on the pattern of `SOCIAL_UNLINKED`),
  and /admin draws a null as a deleted account. `purge.test.ts` gains `invitee_user_id` in `ACCOUNT_COLUMNS`
  (`inviter_user_id` is already there) and reads `INVITES_UNLINKED` as it reads `SOCIAL_UNLINKED`, so the coverage
  check sees both columns and fails if either is left. A reservation never names its invitee, so nothing else holds the newcomer's id.
- `admin_events` rows about invites already follow the shipped admin-events rule.

### Admin writes (PR 2 library, PR 6 screens)

- **Set** an account's invites left (M2) to N, refusing below 0 or above `ALLOWANCE_MAX`: writes `held = N + holding`
  under the sender's lock (the invariant above); history line `history.set`. A waiting reservation stays waiting, as
  the pending sentence says.
- **Top up** a group (M3): raises every member whose LEFT is below N to N left (each under its lock, in user id order),
  in one transaction, lowers nobody, stores no group count;
  one history line `history.topUp` with the raised count.
- **Revoke** a waiting reservation (R12): under the sender's lock, `revoked`, address erased, Clerk's
  `revokeInvitation` after commit.
- History also records `joined` (the spend) and `sent` (an email send or a claim), as `admin_events` kinds of their own.
