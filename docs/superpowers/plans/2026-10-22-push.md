## Rulings (closed, from the handoff and the orchestrator)

- Web push only; six kinds (`FEED_KINDS`), each with its own push toggle, separate from its feed toggle. Default on: `spare-request` alone.
- Delivery A: each event as it happens; several of one kind from one job are ONE push; nothing 21:00 to 09:00 in the
  DEVICE's time zone (what waited goes at 09:00, one per kind); no quiet-hours setting; no push while a client is focused.
- iPhone only from the Home Screen (iOS 16.4+). Tick-driven ask, never on load. Ticks are the account's; the device switch is per device.
- New switch `PUSH_ENABLED`, off in production, held in `ALL_FEATURES_EXCLUDED` until close-out. Code fails closed and stays dormant without VAPID keys.
- The sender reuses the feed writers as the one trigger and honors each kind's push toggle.

## Decisions (D1 to D5), for d9 to confirm

- **D1. The outbox, not a direct send.** `recordFeedItem` takes an `Executor` and its callers are mostly inside a
  transaction (`spare-requests.ts`, `price-drop.ts`), so a send from the writer could go out for a row that rolls back.
  Each writer, when `recordFeedItem` returns true (a NEW item: the dedupe is free), writes a `push_outbox` row in the
  SAME transaction when the reader has a subscription and the kind is ticked. Delivery is a flush: a cron
  (`/api/cron/push-flush`, every 5 minutes, `CRON_SECRET`, like `account-sweep`) is the guarantee, and a writer with a
  request context also `after()`-kicks a flush for that reader, so a spare ask or a collection-triggered match goes out in
  seconds. Job-originated kinds (price drop, new set, new precon) wait at most one cron tick, which suits a batch event.
- **D2. Catalog kinds have no per-user row.** `new-set`/`new-precon` are read from `catalog_first_seen`, never stored in
  `feed_items`. The catalog refresh's end (never under the `catalog-ingest` lock) enqueues one outbox row per subscribed
  reader with the kind ticked, with `batch_key` = the refresh stamp, and only for arrivals the reader's feed would show
  (the shipped baseline rule: a baseline run is never an arrival).
- **D3. `push_kinds` is a map `{kind: enabledAt}`, not a list.** Same shape as `feed_kinds`. A list would push yesterday's
  set the moment a reader ticks new-set; with `enabledAt` only items after the tick send. Unset reads
  `{spare-request: <account created>}`. This is storage, not UX: the handoff's "closed set, unset reads spare-request" holds.
- **D4. Seen is a cursor, so G5's "marks that key seen" cannot be per key.** `feed_seen_at` and `friends_seen_at` are
  cursors. A tap on a Home landing (price drop, combo, every collapsed push) already marks seen through Home's `after()`;
  `/friends` (spare request) already marks through `markFriendsSeen`. The set, precon and friend-page landings do not,
  and moving the cursor from them would hide items the reader has not seen. Decision: no per-key marking; those landings
  leave their item unseen until the reader's next Home visit. Opening Home closes ALL delivered notifications (it marks
  every unseen item seen, so every notification is stale). No new seen state.
- **D5. A focused client and iOS.** Skipping `showNotification` for a focused client is fine on Chrome and Firefox. WebKit
  (an installed iPhone app) requires every push to show a notification and revokes a subscription that stays silent. The
  worker therefore skips only off iOS, and on iOS shows the notification even when focused (replaced by `tag` = kind, so
  it never stacks). This needs one check on a real iPhone, which only Hugh can do; the plan's PR 3 body asks for it.

## Secrets and config (Hugh sets them himself, in Vercel)

Three variables, on BOTH Vercel projects (`the-99` and `the-99-staging`), each project with its OWN keypair:

| Name | Scope | Sensitive | What |
|---|---|---|---|
| `VAPID_PRIVATE_KEY` | Production | yes | the keypair's private half (base64url) |
| `VAPID_PUBLIC_KEY` | Production | no | the public half; read on the server and passed to the page, never inlined at build |
| `VAPID_SUBJECT` | Production | no | `mailto:` contact the push services see |

`pnpm push:keys` (PR 1) prints a new pair and touches nothing. With any of the three missing `pushConfigured()` is false:
no column, no sends, the cron answers 200 `dormant`, and nothing throws. The switch alone never turns push on.

## Data model (PR 1, one migration)

- `push_subscriptions`: `id`, `user_id`, `endpoint` (unique), `p256dh`, `auth`, `user_agent` (a label, capped), `time_zone` (IANA,
  validated against `Intl.supportedValuesOf`), `created_at`, `last_ok_at`. Per-user: added to `PURGE_ORDER` (the purge test
  computes coverage from `schema.ts`) and to the `user_data_touch` set only if Home or `/decks` reads it (they do not;
  `check:list-cache` decides, not this plan).
- `user_prefs.push_kinds jsonb` (D3). Written only on a change (the stamp trigger moves on any UPDATE).
- `push_outbox`: `id`, `user_id`, `kind`, `item_key`, `batch_key`, `payload jsonb` (the route, the feed item key, the copy fields
  `feedCopy.home` needs), `created_at`, `sent_at`. Pruned after 7 days by the flush. Purged with the account.
- Switch `PUSH_ENABLED`, feature, needs `HOME_FEED_ENABLED`; `flag_overrides` constraint like the other switches.

## Risks and open items

- WebKit's silent-push rule (D5) is from platform documentation, not tested here: PR 3 ships the conservative behavior.
- Cron cadence is 5 minutes (`vercel.json` already runs one at that rate), so a job-originated push can land up to 5 minutes late.
- VAPID rotation invalidates every subscription; documented in `docs/agents/push.md`, not built.
- Copy is placeholder throughout (Hugh's call 3); PR 6 runs `/copy-review`.
