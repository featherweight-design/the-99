# Card scanning — build plan (server matching)

Design: `design/design_handoff_the99_card_scan/` (#1903, R1, READINESS 🟢 approved by Hugh 2026-10-16; audit Yellow with
the resolutions below). Research: `docs/superpowers/research/2026-10-15-card-scan-feasibility.md` (real photos,
2026-10-16). Decisions relayed by d9 for Hugh, 2026-10-16:

- **Server matching.** The phone runs the detector and the dhvazquez fp32 embedder and sends the 256-float
  fingerprint (1KB). The server finds the card. No index download; offline is a possible later step.
- **One model:** dhvazquez (`mtg_card_identification_embeddings@653d88d`, MIT). DINOv2 is dropped.

Audit resolutions carried into the build:

- **None of these** opens search by name: the shipped L2 string, and the lab's `search.ts` reused.
- **No torch is the common case (V8).** iOS torch is unreliable, so the dark state never depends on it.
- **The dwell is pinned during the build** at the lab's measured values (`DWELL_MS` 700, `LOSE_MS` 1400,
  `CHANGE_GRACE_MS` 700, three agreeing answers), and changes only on a new measurement.
- **`CARD_SCAN_ENABLED` lands in PR 1**, needing `COLLECTION_EDIT_ENABLED`. Off: no Scan press, no About entry, and
  the match endpoint answers 404.
- **About at launch** (PR 6), one entry, one `ABOUT_VERSION` bump.

## What server matching changes in the design

D1–D5 (index once: download, progress, resume, top-up) existed to fetch a 27MB index to the device. With the index on
the server they have nothing to show, so they are NOT built. The scan mark drawn on D1–D5 has no other home in R1 and
goes with them. Everything from the viewfinder on (V1–V9, review L1–L4, desktop W4/W6) is built as drawn. The dark
state (V8) gains no network failure state of its own: a failed lookup is the shipped ToastFrame (D5's transient
error), and the viewfinder keeps scanning.

## The endpoint contract (PR 1 serves it, PR 2 calls it)

`POST /api/card-scan/match`

Request, `application/json`:

```json
{ "model": "dhvazquez/mtg_card_identification_embeddings@653d88d", "embedding": "<base64>" }
```

- `embedding` is base64 of exactly 256 little-endian float32 values (1,024 bytes), the embedder's output for the
  detector's crop, **L2-normalised** by the client.
- `model` names the embedder build. The server holds one index built by one model and refuses a mismatch.

Responses (every one `Cache-Control: private, no-store`):

| Status | When | Body |
|---|---|---|
| 200 | a match was run | `{ "index": "all-20261014", "guesses": Guess[], "margin": number \| null }` |
| 400 | body unreadable, not 1,024 bytes, a non-finite value, or norm outside 1 ± 0.01 | `{ "error": "bad-embedding" }` |
| 401 | signed out | — |
| 404 | `CARD_SCAN_ENABLED` off for the reader | — |
| 409 | `model` is not the index's model | `{ "error": "model", "index": "...", "model": "..." }` |
| 503 | the index is empty or unreadable | `{ "error": "no-index" }` |

`Guess` is `{ "oracleId": string, "name": string, "scryfallId": string, "score": number }`: the CARD (oracle), the
printing whose row scored best for it, and that row's cosine similarity in [-1, 1]. At most three, best first, one
per oracle: rows of one card pool into one answer, exactly as the lab's `topOracles` does. `margin` is the first
guess's score minus the second's, null with fewer than two guesses. The client's "Not sure yet" margin gate and the
three-answer agreement read these two fields unchanged from the lab.

**Call rate.** One lookup per STABLE detection, never per frame: the client embeds and asks when the detector's
quad has held still, and again only while the card stays in view and the display has not settled (the agreement
needs three answers). Budget: at most 2 a second per device. Requests are counted in the `card-scan` rate bucket
(observe-only, 150 a minute), so a scripted loop is visible in the logs before any limit is enforced.

## The index on the server

- **pgvector** (0.8.0 is available on staging's Postgres 17; not installed). Migration `create extension if not
  exists vector`, then `scan_index`:
  `scryfall_id uuid`, `face text` (`front` / `back`), `oracle_id uuid`, `embedding halfvec(256)`, primary key
  `(scryfall_id, face)`, and an HNSW index on `embedding halfvec_cosine_ops`. `halfvec` (2 bytes a value, ~53MB for
  103,823 rows) because pgvector has no int8 vector type and fp16 keeps the cosine to about 1e-3, far inside the
  margins the gate reads; the probe measures it against the fp32 gallery.
- **One row per image of the every-printing gallery** (`all`: every paper printing plus a DFC's back, 103,823 rows),
  embedded offline by the research pipeline (`scripts/research/card-scan/`), the same build the phone runs.
  `export_index.py server` writes the rows for the ingest: `scan-rows.json` (keys, oracle ids, the index version
  and model) and `scan-rows.f32` (rows × 256 float32). Derived from Scryfall images, never committed.
- **A query** takes the nearest 40 rows by cosine distance under `hnsw.ef_search = 100`, then pools them by oracle in
  TypeScript (`poolGuesses`, pure, tested) and keeps three. The index version and model live in one
  `scan_index_meta` row, written in the same transaction as the rows.
- **The ingest** (`pnpm db:seed:scan-index <dir>`) replaces `scan_index` and its meta row in ONE transaction, on a
  NAMED target: `SCAN_INDEX_TARGET_URL` and `SCAN_INDEX_TARGET_BRANCH`, never defaulted, checked against the branch
  the database reports by `neon.branch_id` before anything is written (the `pull:staging` rule). It refuses a file
  whose row count, dimension or norms disagree, and fewer than 100,000 rows. Staging first; production's index comes
  later by a copy step, not by a second embedding run.
- The table holds no account data, so the account purge has nothing to add.

## PR split

Each PR is under ~800 lines and ~20 files; the boundaries are named here before the build starts.

1. **Server matching** (lane cd). Migration (extension, `scan_index`, `scan_index_meta`), `CARD_SCAN_ENABLED` in the
   registry (needs `COLLECTION_EDIT_ENABLED`) with its flag function, the `card-scan` rate bucket, `poolGuesses` and
   the embedding decode (pure, tested), `POST /api/card-scan/match`, `export_index.py server`, the ingest script,
   and `pnpm probe:card-scan-match` (a scratch branch off local-dev: ingest, query known rows, refuse a wrong branch,
   compare HNSW against an exact scan). No UI.
2. **Camera and matcher hook** (lane 57, against the contract above). `getUserMedia` rear camera, the detector and
   the embedder on device (the lab's `models.ts`), the stable-detection trigger, the lookup, and the lab's
   `steady.ts` display rules with the pinned dwell. A hook and its tests; no screen.
3. **The viewfinder** (V1–V9, Fast/Normal, the tray and its count card), on PR 2's hook.
4. **Add cards integration**: the Scan press in `add-cards-sheet.tsx` at both widths, `source: "scan"` lines, review
   L1–L4, **None of these** to search by name, Save as the shipped add (one History entry).
5. **The desktop fallback and photos** (W4, W6): a photo is detected, embedded and looked up through the same call.
6. **About and close-out**: the entry from `about · scanning your cards.ts`, the `ABOUT_VERSION` bump, the
   feature-acceptance walk at 390 and 1300.

## Switch rollout

When PR 1 merges, d9 sets `CARD_SCAN_ENABLED` to `'true'` on staging and leaves it unset on production. With it on
and no UI yet, the endpoint is reachable only by a signed-in caller who builds the request by hand.

## Not in this plan

Offline matching (the index on the device), production's index copy, and any model other than dhvazquez.
