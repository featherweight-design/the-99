## Decisions this plan makes (each has one defensible answer; stated so review can check them)

Revised after the orchestrator's review (the-99-d9, 2026-09-23). Items 1–11 of that review are
folded in below. Hugh's rulings A, B and C stand as given.

1. **Who writes, and when.** `writeSynopsis(deckId)` is a server action that **never computes or
   analyzes**. It reads the stored reading through `readStoredReading`, and refuses unless that
   reading is `fresh`. It is called from two places, and nothing else:
   - **An explicit control in the Overview slot**: `Write one`, or `Try again` (ruling A). This
     ships first, in PR 3.
   - **The shell's `useDeckProfile` hook, on a SUCCESSFUL press only**: the branch where
     `result.ok` and the reading answers the list it was asked about. The branch where an edit
     landed mid-press (`fresh: false`, `use-deck-profile.ts` ~183) writes nothing. The trigger
     lives in the shell rather than the panel, because the panel adjusts `prevKind` during render
     and unmounts on a tab switch. This ships in PR 4, together with the credit note (ruling C).
     Until then no press spends a credit, so no credit is ever spent without the player being
     told first.

   A stored reading painted on tab open never writes, and the commit path writes nothing (ruling 7).
2. **Reuse is keyed on the FINGERPRINT alone.** A write is skipped, and spends nothing, when
   the newest shown synopsis has `fingerprint === listFingerprint(deck)`, whatever contract it
   was written under. `wouldSpend` uses the same test. Because of ruling B, a new contract applies
   only to a write for a NEW list: an edit, a revert to the same list and a press spends nothing
   and replaces nothing the player has seen. A catalog refresh never stales a synopsis, because
   the fingerprint does not read the catalog. **A section retry on a synopsis written under an
   older contract** does not mix two contracts in one document. It rewrites the whole synopsis
   under the current contract, as one call, charged per decision 4 (a first write's rule).
3. **Stale.** A synopsis is stale when **`synopsis.fingerprint ≠ the current list`, or the deck
   is `dirty`**. A contract bump alone does not stale it (ruling B, the later word over brief
   §6's first draft, which #898 is being amended to match): the old synopsis keeps showing, and
   the next write uses the new contract. This synopsis staleness is separate from the analysis's,
   and can differ from it. After a press whose write was refused by the allowance or failed
   upstream, the analysis is fresh and the synopsis is stale. That case draws only pieces that
   are already drawn:
   - **the tab**: the old Overview whole, then ruling A's `Write one` line in Round 0's state-2
     chrome, with its credit wording from `wouldSpend`. When the allowance is spent, the reset
     line replaces it. The failure line with `Try again` is drawn only right after this deck's own
     write failed upstream, since it would be false otherwise;
   - **the modal**: 6d's banner, carrying that same line and control in place of Re-analyze.

   Between PR 3 and PR 4, every edit followed by a Re-analyze lands here, which is why that state
   carries a control.
4. **Charge.** `reserveModelCall(tx, userId, "synopsis")` runs in the transaction that inserts the
   pending run row. The outcome's transaction settles it, and only a successful answer spends:
   - **A first write** settles `spent` when at least one section passes, and `refunded` when every
     section is refused or the call fails.
   - **A section retry** (decision 6) settles `spent` only when at least one RETRIED section
     passes. A retry whose retried sections all fail again shows nothing new, and is refunded.

   The rolling 24 hours is the one already built (ruling 5). When the allowance is spent, the
   analysis still runs (it is free and never limited), and the synopsis stays as it was.
5. **One run in flight per deck, and a read-time reaper.** A partial unique index on
   `status = 'pending'`, the same form tuning uses. It is paired with tuning's reaper pattern
   (`src/lib/tuning/reaper.ts`): before every insert and on every read, a pending row older than
   `SYNOPSIS_REAPER_CUTOFF_MS` (below `RESERVATION_TTL_MS`; `src/lib/synopsis/reaper.ts`) is failed as `interrupted`, and its
   unit refunded. A crashed write therefore never locks a deck out. A late result from a reaped
   run finds no row under its own `where status = 'pending'` guard, and discards itself.
6. **Try again on a partly refused synopsis rewrites only the refused sections** (finding 11).
   The passing sections are sent back as context and kept byte for byte, which makes the modal's
   *"The rest did"* true. `retrySynopsisSections` refuses unless the reading is fresh and the
   synopsis's fingerprint still equals the current list. It is charged per decision 4.
7. **The version copy is written at commit only, and never after.** The commit's existing
   `after()` gains one call, `pinSynopsisToVersion(deckId, userId, committed)`, beside
   `pinAnalysisToVersion`, with the same guards (the list must match, and only the newest
   version). It is **insert-if-absent** (`on conflict do nothing` on the `version_id` pk), so a
   version's copy is immutable. The press-time pin is dropped. The record line *"Written for
   version 3 when it was committed"* (`SYNOPSIS-modal.md` §4.4) is then true by construction.
   A pulled card's automatic commit writes no prose and, having moved the list, pins nothing.
8. **Model.** `SYNOPSIS_MODEL = "claude-sonnet-5"`, a named constant in `src/lib/synopsis/model.ts`,
   stored on every run. Nothing branches on its value.
9. **`wouldSpend`, computed on the server.** `fetchSynopsis` returns
   `{ synopsis, stale, allowance, wouldSpend }`. `wouldSpend` is true exactly when a press would
   actually write an overview: no shown synopsis for the current LIST (the fingerprint alone,
   decision 2 and ruling B; a contract change never counts), a fresh reading to write from, and
   at least one unit left. The credit note keys on `wouldSpend` and never on `stale`: after a
   revert to the written list the banner shows while the overview is still current, and the note
   must not promise a credit the press will not spend (credits audit, finding 4). It is computed on the server because `listFingerprint` is server-only. The shell's
   synopsis state refetches it on each of these:
   - tab open;
   - every press settle;
   - every write or retry settle;
   - every change of the hook's list key (an edit made on another tab).

   It drives the credit note (PR 4) and the `Write one` line's credit wording (PR 3).

10. **No probe or dev server can spend by accident.** Under `next dev` (`NODE_ENV ===
    "development"`), `generate.ts` calls the model only when `SYNOPSIS_LIVE=1` is set. Otherwise
    it calls `src/lib/synopsis/stub.ts`, a fixture reply shaped per the schema. `SYNOPSIS_STUB`
    switches the stub to a partial, a refused-all, a malformed or a busy outcome, and stored runs
    record `model = "stub"`.
    - So `probe:synopsis-ui` and PR 4's probe, which press `Write one` and Analyze against a
      local-dev `pnpm dev` server, cannot reach the real model. Each also asserts `model = "stub"`
      on the first row it writes, and aborts otherwise.
    - `probe:synopsis --live` is the only path that sets `SYNOPSIS_LIVE`, in its own process and
      under its cap.
    - Deployed builds (staging and production, both `next build`) call the real model, with no
      flag.

## The accept contract

The reply is a zod schema, which constrains its shape server-side. Every rule below is the app's
own check. A failing section is **refused, with a reason**, and never trimmed or partly shown.

- **Card names are marked** in the prose as `[[Name]]` and resolved against the deck's cards
  (full name, and each face of a two-faced card). Printed and flavor names are not resolved: the
  prompt hands the model oracle names only, and asks for them exactly. In Weaknesses they are resolved against the
  catalog. An unresolved mark refuses its section (`unknown_card`). A resolved mark renders as the
  card-open trigger. A deck card of two words or more named WITHOUT its mark refuses its section
  (`unmarked_card`), since it would render as text that opens nothing.
- **Key tips are structured:** `{ cards: string[], text }`, with at least 2 cards, all in the deck,
  and each one marked in its own `text` (`tip_not_in_deck`, `tip_too_few_cards`).
- **Key cards** are `{ card, claims: Category[], job }`. `claims` is drawn from the categories the
  app classifies: the five roles from `classifyRoles`, `tutor`, `combo piece` (from the profile's
  combos) and `commander`. Every claim must be one the profile holds for that card, and the `job`
  text may not use a category's words (ramp, draws, removal, wipe, tutor, combo) the card does not
  hold (`job_unsupported`). An engine or finisher with no classified role is allowed, with no
  claims.
- **The mulligan's figures are the app's.** `facts.ts` derives each one from the profile:
  - **the land count** is `counts.landCapable`, because a modal double-faced land is a land drop;
  - **the ramp count** is `roles.counts.ramp`;
  - **the keepable land range for an opening seven**: with `L = landCapable` and `e = 7·L/99`
    (the expected lands in seven), the low end is `max(2, floor(e) − 1)` and the high end is
    `min(5, ceil(e) + 1)`. At 36 lands that gives 2–4. The rule is stated here and unit-tested in
    PR 1's `facts.test.ts`;
  - **the colours** are named from `colours.identity`, with any colour in `colours.unproducible`
    named as a gap.

  There is no per-colour source count: the profile holds only `producibleColors`, an approximate
  union, so no figure is invented for it. Any numeral in a Keep or Send back line must be one of
  the passed facts (`uncomputed_figure`).
- **No strength claims** (brief §2.2, §5), in any section: bracket, power, cEDH, optimized,
  competitive, casual, tier, score, rating, `n/10`, and strength adjectives. Game facts such as
  *deals 16* stay allowed; the rule forbids strength words, not numbers (audit §3, row 3).
  Failing this gives `strength_claim`.
- **Counts and budgets** follow `SYNOPSIS-modal.md` §4.2: Overview is 1 paragraph; Core strategy
  3–5 steps; Keep 2–3 and Send back 2–3; Key tips 2–4; Key cards 5–8; Weaknesses 1–3, untiered.
  The line budgets become character budgets measured from the rendered measure at the tighter of
  the two widths, the same method as `commander_support.prose`. **The budget is a design value and
  is never loosened to make generation pass** (brief §4.2). Failing this gives `over_budget`.
- **Whole sentences only.** Text that does not end in terminal punctuation is refused
  (`partial_sentence`).
- **The per-section count** the refused slot draws (*2 of 7 cards failed checking*) is failed
  checks over the checks run in that section.

## Measurable outcomes (for the eval harness, sub-project 10)

Every run ends in one typed outcome, stored on its row, in tuning's vocabulary:

| outcome | meaning |
|---|---|
| `survived` | every section passed |
| `refused` | at least one section failed; `content.verdicts` holds each one's `{ section, status, reason, failed, total }` (partial and total refusal both land here, and the jsonb says which) |
| `malformed` | the reply failed the schema after the client's one retry |
| `upstream_busy` / `timeout` | the client's own classes, unchanged |
| `interrupted` | written by the reaper, for a pending run older than `SYNOPSIS_REAPER_CUTOFF_MS` |

Each row stores `model`, `contract_version`, and `input_tokens` / `output_tokens`. The token
columns are **nullable**, because `callModel` returns `usage` only on success
(`src/lib/model/client.ts` ~31), and after its one retry it reports the second attempt alone. A
failed run therefore records no tokens. A retried success understates its cost by the first
attempt, and the column comment says so. `src/lib/model` is not changed. If the harness needs
per-attempt usage, that is a request routed to `tuning`. The harness counts from the table and
needs no log scraping.

## Storage (one migration; next free number, taken after a fetch)

- `deck_synopses`: one row per generation run, kept and never replaced, like tuning's runs:
  `id`, `deck_id` (cascade), `user_id`, `fingerprint`, `contract_version`, `model`,
  `model_call_id` → `model_calls`, `status` (`pending|done`), `outcome`, `content` jsonb (the
  checked sections, each with its status and reason), `input_tokens` and `output_tokens`
  (nullable, see Outcomes),
  `retry_of` (null, or the run a section retry built on), `created_at`. The index is on
  `(deck_id, created_at)`, plus the partial unique index on pending. The draft's synopsis is the
  newest `done` row with a shown section.
- `deck_version_synopses`: `version_id` pk → `deck_versions` (cascade), and `synopsis_id` →
  `deck_synopses`. Written once at commit, insert-if-absent, never updated. It never goes stale
  (`SYNOPSIS-modal.md`).
- `model_calls.feature` already admits `'synopsis'`. There is no change there.

## Rulings from this plan (Hugh, 2026-09-23)

A. **A current reading with no synopsis offers `Write one`.** That covers readings stored before
   launch, and an Analyze whose model call failed upstream on an unchanged list. The Overview slot
   draws one line and **Write one**, charged like any write. After an upstream failure it reads
   *We could not write the overview just now. Nothing about your deck changed.* with **Try again**.
   This uses Round 0's state 2 and state 4 chrome, with the copy through `/copy-review`. It lands in
   PR 3, and `writeSynopsis` is its action (PR 2).
B. **A contract bump is not an edit.** The existing synopsis keeps showing, and no banner claims the
   deck changed. The new contract applies at the next write after an edit. **This departs from brief
   §6** (as updated on #898), which treats a moved contract version as stale. Hugh's answer is the
   later word, and the brief needs a one-line amendment (flagged to the-99-d9).
C. **The Re-analyze credit note goes to Design.** Design draws its placement at 390 and 1300 before
   it is built. The backend PRs are not held. PR 4 builds the note from that drawing. If the drawing
   has not landed, PR 4 waits for it. Until PR 4 ships, no press writes; the Overview's own
   control (ruling A) is the only writer, and it states its credit. So ruling 3 (warn before
   spending) is never broken. The Design prompt should cover the first Analyze as well as
   Re-analyze, since both write from PR 4 on.

D. **A stale synopsis beside a fresh analysis** (Hugh, 2026-09-23, relayed by the-99-d9). Option 1,
   the composition in decision 3: the old Overview stays whole, followed by ruling A's `Write one`
   line in state-2 chrome, with its credit wording (the reset line when credits are spent). The
   modal's 6d banner carries the same line in place of Re-analyze. There is no Design round, and
   PR 3 is not held.
