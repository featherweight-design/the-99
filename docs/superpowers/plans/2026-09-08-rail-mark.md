### The sign-off item, resolved

> *"23px numerals against the brand sheet's 24px crown-drop floor."*

The floor does not bind here. In the brand sheet (`brand/The 99 - Brand Sheet.dc.html`, § 01) the
sentence *"Below 24px the crown drops away; the brass numerals alone carry the mark"* captions the
**app icon / favicon size ramp** — three tiles at 64, 32 and 16px. The 64 and 32 tiles draw the
crown; the 16 tile does not. The measurement it governs is the **tile**, not the numeral's
font-size: the 32px tile keeps its crown while drawing numerals at 15px, well under 24.

1a's head is a 39px lockup. It is above the floor on the floor's own terms, so no exception is
being taken and Design's careful hedge is not needed. The ruling stands as drawn; nothing in the
handoff changes. There is no question left for Design, so no prompt is emitted.

### The three arithmetic corrections

Both come from the same source: **the canvas draws the crown as three flex-laid `<span>`s; the app
draws it as one SVG that already does the rotation maths.**

1. **The gap is 3, not 6.** `crownBox()` in `src/components/ui/crown.tsx` composes the row as
   `s√2 + gap + l√2 + gap + s√2` — its `gap` is the space between the rotated diamonds' *points*,
   which is exactly the handoff's "3px of visible air". The handoff's 6px is the CSS number needed
   to produce that air on unrotated layout boxes (`gap = air + 0.207 × (w₁ + w₂)`), and the app
   needs no such conversion. Passing 6 would double the air. The handoff's own note — *"if the
   crown is ever rebuilt as an SVG the arithmetic disappears — which is the better end state"* —
   describes work that already shipped.

2. **The crown row is 35px wide, not 32.5.** 32.5 is the flex layout box (`6 + 6 + 8.5 + 6 + 6`);
   the drawing overflows it, because rotated squares do. The real extent is
   `6√2 + 3 + 8.5√2 + 3 + 6√2 = 35.0`. The height is unaffected — `8.5√2 = 12.0`, exactly the 12
   the handoff states — so the **39px lockup is correct as written**, and 39 is the number the
   layout actually depends on. The 2.5px of extra width is centred in a 62px rail.

3. **The nav block drops 17px, not 13.** The handoff's own head-zone figures are right: today's
   zone is `14 + 26 + 16 = 56` and the new one is `14 + 39 + 20 = 73`. 13 is the head's own growth
   (26 → 39) counted alone; the spacer grows too (16 → 20), and the difference of the two zones is
   17. Measured in the browser after the change, the `Primary` landmark starts at 73.02px from the
   rail's top, which is the handoff's 73 and not a number this plan chose. Nothing needs building
   differently — only the acceptance figure is restated.

### The dead variant

`Crowned99` has four variants. Three have callers: `hero-mobile` and `hero-desktop`
(`src/app/page.tsx:32–33`) and `mobile-header` (`nav.tsx:324`). **`"rail"` has none.** It is
reachable only through the `variant = "rail"` default parameter, which no call site relies on.

It is the *wide* rail's wordmark — 6/8/6px diamonds, 30px numerals at weight 800, still documented
at `docs/superpowers/design-tables/appshell.md:1801` and § *Rail: Wordmark area*. That rail was
replaced by the 62px icon-only rail in the 2026-09-07 refresh, and its wordmark went with it. So
the handoff's "renders in the wide rail" is describing a surface that no longer exists; the true
statement is that at desktop width the mark renders **nowhere**, which makes its case stronger, not
weaker.

So `"rail-62"` is not added *beside* `"rail"` — it **replaces** it. Adding a fifth variant would
leave dead config next to live config with near-identical names, which is the more expensive of the
two outcomes and the one a reader has to disambiguate every time. Design's name is kept as ruled:
`rail-62` says which rail, and the wide rail is not coming back under it.

Two consequences:

- The `variant` prop becomes **required**. Its only purpose was to default to the dead variant, and
  all three call sites pass it explicitly.
- `appshell.md:1801`'s `Rail wordmark` row is marked retired and a `Rail head (62px)` row is added
  beside it, so the conformance table records what the rail draws now. The § *Rail: Wordmark*
  sections are left as the historical record of the wide rail, which is what they already are.

### Not adding `shellCopy.railMarkAria`

The handoff's copy file asks for the head's accessible name to live in `src/lib/copy/shell.ts`.
It is already in the codebase, correct, at the only sensible owner: `Crowned99` renders
`role="img" aria-label="The 99"` on its own `<svg>` for **all four** variants. The copy file was
written for a head that is a bespoke `<span>` in `nav.tsx`, which is what ships today and what
this change removes.

Adding the string would put a second source of truth for a name three other variants already
render from the component, and would make `marks.tsx` — a generic mark file used by the hero and
the signed-out page — import shell chrome copy. The requirement (*"screen reader announces The 99
once, before the Primary nav landmark"*) is met without it, and is asserted in a test below.

## The changes

Four files, plus the handoff and this plan.

### 1. `src/components/marks.tsx` — one variant swapped for another

Replace `"rail"` with `"rail-62"` in `Crowned99Variant` and in `CROWNED99_SPECS`:

```
"rail-62": { smallDiamond: 6, largeDiamond: 8.5, numeralSize: 23, fontWeight: 900,
             gap: 3, translateX: 0, baselineGap: 22, bottomPad: 5,
             letterSpacing: "-0.01em" }
```

Drop the `variant = "rail"` default; the prop is required.

`baselineGap` and `bottomPad` are new per-variant fields, replacing spacing that was hardcoded in
the render body. The three surviving variants are given the values that reproduce what that body
computed for them (`baselineGap = numeralSize + 6`, `bottomPad = 4`), so **their output is
unchanged after the refactor** — the tests below assert the rendered geometry explicitly rather
than trusting that.

- `baselineGap = 22` is the distance from the crown row's bottom to the numeral baseline, and it
  is **not** the handoff's `4 + 23 = 27`. The canvas sets these numerals as HTML with
  `line-height: 1`. Cinzel 900's ascent and descent sum to 31px at this size, so a 23px line box
  carries −4px of half-leading and pulls the baseline 4px up inside its own box: 4 + 23 − 4 = 22.
  An SVG `<text>` has no line box, so the em-box reading of the handoff drops the digits 5px and
  opens a visible trench under the crown. This was caught in the browser walk, not on paper, and
  is why the walk is a task rather than a formality — it only shows up here because this variant's
  crown-to-numeral gap is 4px rather than the hero's 98.
- `bottomPad = 5` completes the 39px lockup the rail's 73px head zone is measured from: the
  baseline sits at 12.02 + 22 = 34.02, and 5 more makes 39.02.
- `translateX = 0`: the offset exists to optically centre a crown over a numeral pair, and the
  existing values track numeral size (−3 at 132px, −1 at 30px, 0 at 24px). At 23px it is 0.
- `letterSpacing: "-0.01em"` matches the canvas's tracking on the numeral pair.

### 2. `src/components/shell/nav.tsx` — the head slot

Replace the diamond `<span>` (`nav.tsx:155–161`) with `<Crowned99 variant="rail-62" />` and change
the spacer `mb-4` → `mb-5` (16 → 20px). The `data-nav-diamond` attribute goes with the span; the
comment above it is rewritten to state the new rule and cite `CHROME-rail-mark.md`.

### 3. `src/components/shell/nav.test.tsx` — the once-at-the-top assertion

`"carries the app mark once, not once per row"` currently counts `[data-nav-diamond]`. It becomes
a role query — `within(rail).getAllByRole("img", { name: "The 99" })` has length 1 — which asserts
the same rule *and* the accessible name, and no longer depends on a test-only attribute. Add a
second assertion that the mark precedes the `Primary` navigation landmark in document order.

### 4. `docs/superpowers/design-tables/appshell.md` — the conformance row

Mark the `Rail wordmark` row (line 1801) as the retired wide rail's and add the 62px head's row
beside it, citing `CHROME-rail-mark.md`.
