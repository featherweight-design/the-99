## Decisions this plan makes

**D1 · The side table, with a dormant state.** `deck_locks (deck_id, oracle_id, created_at, removed_at)`:
- Primary key `(deck_id, oracle_id)`.
- `deck_id` references `decks` `on delete cascade`, and `oracle_id` references `cards`.
- An index `(oracle_id, deck_id)` for Pull it's read, which asks about every deck holding a card.
- Mirrors `deck_proxies` and its doc comment (F1).
- Not versioned.

**Membership** is `deck_cards` only (the audit's engineering notes). A commander is never offered a lock, and no tool cuts one.

**A LIVE lock** is `removed_at is null` AND the card is in `deck_cards`. Every read is scoped that way.

**D2 · How L1 is built. This is the one decision the audit left open, and I need a ruling on it.**

The audit's F2 says the lock ends at removal, and that only the row's Undo and the review screen's Put back restore it. The row's Undo can pass "was locked" from client state. Put back cannot: the review screen lists removals as a diff between the version and the draft, the removal may be sessions old, and a deleted lock row leaves nothing to read. So:
- **At removal the row goes DORMANT, not deleted.** `pruneOrphanLocks` stamps `removed_at` on every live row whose card has no membership. It is one reconcile statement, beside every `pruneOrphanProxies`; the static guard in `prune-proxies.test.ts` extends to require both.
- **A card that returns by any other path returns unlocked.** An `after insert` trigger on `deck_cards` deletes a DORMANT row (and only a dormant one) for the inserted card. This covers the add panel, the fill, a tuning apply, a Take, a pull, an import, `restoreAutoCards`, the top-off restore and a discard's reinsert. A trigger is the one place every add passes through, so no path can forget it (F2's objection to "keep the row"). A LIVE lock is never touched by it: a discard deletes and reinserts every row, and a card that never left keeps its lock, because the prune runs after the reinsert (`versions.ts:319`), never between the two (F1). An upsert onto a row that still exists fires no insert trigger, which is safe, because a card still in the deck never has a dormant row.
- **Undo and Put back REVIVE the dormant row BEFORE the re-add**: `update deck_locks set removed_at = null where … and removed_at is not null`, then the insert, in one transaction after the deck row lock (`addCardToDeck` takes it at `actions.ts:512`). The trigger then finds nothing dormant to delete. Reviving after the insert would find nothing, because the trigger fires in the insert's own statement. `relock` means "revive a dormant row if there is one", never "lock": the client cannot assert a lock the server does not hold, and it is gated on the switch.
- **All three Undos:** the row's (`decklist-row.tsx`), the card view's `UndoTile` (`deck-card-undo-tile.tsx:32`; a tile's ✕ removes a card too, `deck-card-tile.tsx:155`) and the review screen's Put back.
- **A commit deletes the deck's dormant rows**: the removal stayed, so "the lock ends only if the removal stays".
- **A discard brings a removed locked card back LOCKED** (Hugh, 2026-09-25, Q1): the discard undoes the removal, so the lock never ended. In the discard's transaction, BEFORE the reinsert: revive the dormant rows whose card the version holds (`removed_at = null`). The reinsert's trigger then finds nothing dormant for them. AFTER the reinsert, delete whatever is still dormant (a card added and locked after the commit, then removed: the version does not hold it, so it does not come back at all).
- **`setCardLocked` inserts with `on conflict do update set removed_at = null`**, so a stray dormant row can never swallow a lock.

The alternative is no dormant state, with Put back returning the card unlocked. That contradicts L1, so I have not planned it. `probe:locks` proves the trigger, since no unit test here can reach one.

**D3 · The switch.** `neverCutEnabled(env = process.env)` in `src/lib/decks/never-cut-flag.ts`, following the `swapToolsEnabled` / `noticesEnabled` pattern, with the same test table. Off means:
- no lock surface draws;
- `setCardLocked` refuses;
- no filter runs anywhere.

The filters are gated too, not only the UI. With the switch off, a lock row that exists (written on staging, say) must not change what production's tuning or sweeps do. The switch is added to `.env.example` and `docs/deployment.md`, `true` on staging, and unset on production until Hugh walks the feature.

**D4 · Filters, never instructions (the brief).** Every enforcement point reads the lock inside its own transaction, after the deck row lock where it takes one. The prompt tag (F4, `lockedCardsCopy.tuning.promptTag`) tells the model, but the validator is what guarantees it: a suggestion cutting a locked card is dropped with its own `neverCut` key, which the lead does not count (F4).

**D5 · The lock stays out of the stored analysis** (F6a). The climb sheet and the tuning pack take the lock set as an input, the way the pack takes `owned` (`evidence.ts:97-105`). Toggling a lock never marks the analysis dirty, and it does not call `touchDeck`, because a lock edits no list (F12).

**D6 · Tuning's gate hashes the locks** (F9). The sorted live lock ids join `FingerprintInput`, so locking a card reopens a run on an unchanged list.

**D7 · Revalidation is deferred** (F12). `setCardLocked` revalidates this deck, its tuning set and `/decks/[id]/changes` (by pattern, as `revalidate-claims.ts:41-48` does) in `after()`, never inline. The review-screen pattern matters because of L2: another deck's review page must stop offering Pull it from this deck once the card is locked here. The mode invites a run of toggles, and each would otherwise re-render the page into its reply.
