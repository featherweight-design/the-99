# Admin: flags and model costs

Design brief, 2026-10-11. Asks for a FULL Design round on a new, Hugh-only admin area with two jobs:
turning features on and off for the whole app, a named group or one account without a redeploy, and
reading what the model features cost, by period, feature, model and account, well enough to budget
ahead. Nothing here is built. This brief says what exists, what is ruled, what engineering has locked
and what Design owns. Hugh asked for a full round rather than a light pass: a lighter admin in another
app needed several revisions.

## Rulings 2026-10-11 (Hugh), closed

These are decided. Do not reopen them in the drawings; open questions are at the end.

1. **Environment variables stay the default and the kill switch.** Each feature's `*_ENABLED` variable
   keeps its meaning. A database table holds OVERRIDES on top of it: app-wide on or off, per account,
   and per named GROUP (`friends`, `testers`).
2. **Precedence: account or group, then app-wide, then the environment.** The most specific override
   wins. A change takes effect without a redeploy.
3. **Model costs, five readings.**
   - Totals by period against the caps: the account's monthly cap, the $15/month ceiling on system
     spend, and per-feature caps such as the Overview accuracy line's $15.
   - By feature and model: model, effort, calls, cost per call, month total.
   - Per account: spend, and credits used against the allowance.
   - Eval and development spend, read from the eval ledgers committed in the repo.
   - Anything granular that helps budgeting ahead: trend, projection to month end, cost per active
     account, cost per press by feature, reservation against actual.
4. **An outline of which feature or job calls which model at which effort** (the table under *What
   exists today*), so a model change is visible in one place.
5. **Access: Hugh only.** A server-side allowlist of Clerk user ids. Everyone else gets a 404, not a
   refusal page.
6. **A full Design round**, phone and desktop.

### Where switches reach a cache or a cookie

- **Home and `/decks` cache their whole payload per reader** (`cachePageForUser`,
  `src/lib/cache/page-cache.ts:48-70`). The key carries a `switches()` string built from five switches
  (`page-cache.ts:36-39`: analysis tab, notices, change commander, never cut, tuning) read from the
  environment, beside the reader's data stamp. Every other `cacheForUser` key carries the deployment
  (`src/lib/cache/deployment.ts`), which is how a switch flipped by redeploy retires entries today.
  Home reads `analysisTabEnabled()` inside its cached load (the load opens at `src/app/page.tsx:117`,
  the read is `:142`); `/decks` reads it in the page body (`src/app/decks/page.tsx:41`) before the
  load opens at `:46`, and the load captures the result. Either way the value reaches the payload, so
  the resolver must cover both placements.
- **About.** Each About entry carries the switch of its feature (`switch:` in `src/lib/copy/about.ts`,
  for instance `:526`, `:617`, `:1113`), and `SWITCHES` in `src/lib/about/visible.ts:28-44` reads each
  through the feature's own flag function. The proxy computes `visibleEntries()` on every gated request
  and keys its fast-path cookie on the visible entries (`src/proxy.ts:52-54`), so a switch flip retires
  the cookie and the sheet decides again.
- **The client never reads a variable.** Four client components mention a flag
  (`got-it.tsx`, `analysis-panel.tsx`, `synopsis-overview.tsx`, `analysis-empty.tsx` in
  `src/components/decks/`) and all four receive it as a prop from the server.

- **`model_calls`** (`src/db/schema.ts:1932-1960`): one row per model RUN. `feature` in `tuning`,

## What engineering has locked

1. **One resolver, and every switch goes through it.** Each flag function keeps its signature,
   `fooEnabled(env)`. A resolver builds, per request and per reader, an env-shaped object in which each
   switch's variable is replaced by its resolved value, and passes it in. Compound rules (`TUNING`
   needs `ANALYSIS_TAB`, `SHOPPING_MARK_BOUGHT` needs `COLLECTION_EDIT`) stay in the flag functions, so
   an override of a child never turns on a parent.
2. **Resolution order, per switch:** an account override; else a group override (when the account is in
   several groups that disagree, OFF wins; open question 1 asks whether Design wants it shown); else the
   app-wide override; else the environment variable. An override row is `on`, `off`, or absent; there
   is no "inherit" value, absence is inheritance.
3. **The environment is still the kill switch.** A variable set to the literal `off` (a new value, not
   `false`) refuses every override for that switch, so a bad override can always be beaten by a
   redeploy. Every other value keeps today's meaning.
4. **Tables.** `flag_overrides` (switch name, scope `app` | `group` | `user`, `group_id` set for a
   group override, `user_id` (Clerk id) set for an account override, value on/off, note, updated by,
   updated at); `flag_groups` (name, description); `flag_group_members` (group, `user_id` (Clerk id),
   added by, added at). Switch names are a closed set in code, checked by constraint. Integrity, by
   constraint: an `app` row has neither `group_id` nor `user_id`; a `group` row has `group_id` and no
   `user_id`; a `user` row has `user_id` and no `group_id`. Unique on (switch, scope, `group_id`,
   `user_id`) with nulls not distinct, so each target holds at most one override per switch and the
   resolution is deterministic. Clearing an override deletes its row (absence is inheritance); the
   history lives in rule 5.
5. **Audit trail.** `admin_events`, append-only: who (Clerk id), when, `kind` (`override_set`,
   `override_cleared`, `group_created`, `group_renamed`, `member_added`, `member_removed`), and the
   fields that kind needs: switch, scope, `group_id`, `user_id`, old value, new value, note. A check
   constraint ties each kind to its required fields, so a membership change is as representable as an
   override change. Nothing is ever deleted from it.
6. **Cache keys carry the reader's RESOLVED switches.** `switches()` in `page-cache.ts` reads from the
   resolver, not from `process.env`, and covers every switch a cached loader reads, not five of them.
   The deployment stays in every key. A flip therefore retires exactly the readers it changes, with no
   redeploy and no invalidation call.
7. **Freshness.** Overrides are read once per request through a short process cache (about 30 seconds),
   and the admin's own write clears it in that instance. "Takes effect" means within that window on
   every server; the UI says so rather than promising instant.
8. **`check:list-cache` will see the overrides tables, and must say why they are safe.** `page-cache.ts`
   will import the resolver, and the check follows Home's and `/decks`' imports through `src/lib`
   (`scripts/lib/list-cache-tables.mjs:13-19`), so `flag_overrides` and `flag_group_members`, which
   both carry a `user_id` column (rule 4; the check's `OWNER_COLUMNS`), will be reported as per-user tables with no `user_data_touch` trigger. A trigger
   would be the wrong fix: an app-wide or group override changes many readers and a per-row trigger
   bumps one stamp. The resolved switches are in the key (rule 6), so a cached page cannot outlive an
   override. The check learns that category explicitly (a table whose content reaches a cached page
   only through its key), pinned by a test that no cached loader imports the resolver. No column is
   renamed to slip past the check.
9. **About follows the resolved switches.** `visibleEntries(env)` and the proxy's cookie take the
   resolved object, so an account switched on sees that feature's entry and its sheet, and an account
   switched off does not. Turning a feature on for a group will show its members the What's new sheet;
   that is the intended behavior, stated in the UI (open question 6).
10. **Access.** `ADMIN_USER_IDS`, a comma-separated server-only variable, read in one module. Every
    `/admin` route and every admin server action checks it on the server and calls `notFound()` for
    anyone else, signed out included; the route is absent from the shell's navigation for them, and no
    client bundle carries the list. Hugh's id is the only entry.
11. **Costs are read, never written, by the admin.** Every figure comes from `model_calls`,
    `card_label_batches` and the committed eval ledgers (bundled at build time; they move only by a
    merge). Caps that live outside the code (the account cap, the system ceiling) are a small settings
    table the admin edits, so the bars have a line to draw against.
12. **Each environment administers itself.** Staging's admin reads staging's ledger and overrides, and
    production's reads production's. No cross-database reads.
13. **One usage row per provider call, from the build on.** A child table, `model_call_parts` (the
    `model_calls` row, step name, model, effort, the four meters, cost), written wherever
    `recordModelUsage` writes today, so a two-step run records each call with its own model and
    effort and the parent row keeps its role as the allowance's reservation. The by-model and by-effort
    views read the parts. Rows from before it have no parts: the dashboard shows them by feature, with
    a composite model such as `claude-haiku-5-5+claude-sonnet-5-5` named as such and effort unknown,
    never split by guesswork.

## What Design owns

- **The information architecture.** Where `/admin` lives (a door in the account menu for Hugh only, a
  separate shell, or both), and how flags, groups, accounts and costs divide into pages or tabs.
- **The flags list.** All 21 switches: name, a one-line plain description, the environment value, the
  app-wide override, how many groups and accounts carry an override, and the RESOLVED state for "most
  readers". Compound switches show their parent. Model features are marked as such. Filtering by
  state and search by name.
- **The flag detail.** Set or clear the app-wide override; add or remove a group or account override;
  the note field; the resolved state for a sample account; the audit history for this switch. The
  confirmation for a change that turns a MODEL feature on for more accounts (it spends money).
- **The groups editor.** Create, rename, describe a group; add and remove members by account lookup;
  which switches the group overrides.
- **Account lookup.** Find an account (by Clerk id, email or name; open question 4), and see in one
  place its groups, its resolved switches with where each came from, its credits today against its
  allowance, and its spend this month.
- **The cost dashboard.** Period totals against the caps (account cap, system ceiling, planned budget,
  owner share, per-campaign caps); a trend with the projection to month end; feature by model with
  calls, mean and p90 cost per call, and the month total; player against system; refunded dollars;
  reservation against actual; cost per active account; the eval ledgers as their own block. Charts are
  Design's to choose; the dataviz rules in this repo's design system apply.
- **The model usage outline.** The table above, drawn as a reference page: feature, model, effort,
  origin, where the constant lives, and the last month's cost beside each.
- **Empty and sparse states.** Staging has one account and six active days: the dashboard must read at
  that density and at production's.
- **Phone and desktop** both, in the same round. The phone is for checking a figure or killing a
  feature away from a desk; Design decides how much of the dashboard it carries.
- **Copy.** Every string goes through `/copy-review`. Vocabulary: a member is *selected* or
  *unselected*, never ticked; a switch is *on* or *off*.

## Open questions

1. **Group disagreement.** An account in two groups whose overrides disagree resolves OFF (locked rule
   2). Is that shown on the account page as a conflict, or simply as the result with its source?
2. **Infrastructure switches.** `LIST_CACHE_ENABLED`, `ABOUT_SHEET_ENABLED` and `HOW_IT_WORKS_ENABLED`
   are not features a friend tries. Are they listed with the rest, grouped apart, or app-wide only?
3. **Job switches.** Do the GitHub variables (`CARD_LABELS_ENABLED`, `PROSE_MAX_USD` and the rest) show
   read-only on the admin, or stay off it entirely? Writing them is out of scope.
4. **Finding an account.** The app stores only Clerk ids. Does lookup show names and emails fetched
   from Clerk, or ids with a nickname the admin types?
5. **What a cap does.** The account cap and the system ceiling are drawn as lines. Should the admin
   also set the app's `BUDGET_USD` and `OWNER_SHARE_USD`, or are those still code constants shown
   read-only?
6. **The sheet on a flip.** Turning a feature on for a group shows its members the What's new sheet
   (locked rule 9). Does the flag detail warn before the change, and can a change be made silently?
7. **Concert Crawl.** The Anthropic key is shared, so the account cap covers both apps and the app's own
   ledger cannot see the other's spend. Draw the cap with an "elsewhere" remainder entered by hand, or
   leave the account cap off until Anthropic's usage and cost reporting is wired (a separate admin key)?
8. **Labels in the ledger.** The October label runs sit only in `card_label_batches`. Read both tables,
   or backfill system rows into `model_calls` first so the dashboard has one source?
9. **Periods.** UTC calendar month is how the bill and the spend cap count. Are week and custom ranges
   wanted, or month only with a daily trend?

## Prior art

- **LaunchDarkly** (docs.launchdarkly.com, *Targeting*): per-flag targeting with individual targets,
  reusable segments and a fallthrough default, plus a per-flag change history. The closest model for
  account > group > app > environment.
- **Statsig** (docs.statsig.com, *Feature Gates*): rules evaluated in order, with ID overrides above the
  rules and an audit log per gate.
- **Vercel Flags** (vercel.com/docs/feature-flags, *Flags Explorer*): flags declared in code, overridden
  per browser from the toolbar; the code-declared default with an override on top is this brief's shape.
- **PostHog** (posthog.com/docs/feature-flags): release conditions over cohorts, and an activity log.
- **Anthropic Console** (console.anthropic.com, *Usage* and *Cost*; docs.anthropic.com, *Usage and Cost
  API*): token and dollar charts by day, grouped by model, workspace or key. The reference for the trend
  and the by-model split, and the source open question 7 would read.
- **Stripe Dashboard** (docs.stripe.com/dashboard): period selector with comparison to the previous
  period, and KPI tiles with a small trend beside the figure.

Every one of these serves teams and thousands of flags. This admin has one operator, about 21 switches
and a handful of accounts; the drawings should take the precedence model and the history, not the
density.
