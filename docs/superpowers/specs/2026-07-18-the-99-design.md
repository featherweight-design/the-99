# The 99 — Design Spec

**Date:** 2026-07-18
**Status:** Approved design, pre-implementation

## Overview

The 99 is a web companion app for Magic: The Gathering's Commander (EDH) format. It answers the question every collection owner has: *"What decks can I actually build with the cards I own?"*

Core loop (v1): upload a collection CSV → get ranked, explainable commander recommendations → build a deck from owned cards, with unowned gaps flagged as a shopping list.

Personal project for one user initially, shared with a small circle of friends later — so multi-user from day one, at $0/month infrastructure cost.

## Scope

### v1 (this spec)

- Upload a ManaBox collection CSV
- Recommend viable commanders from the collection
- Build a deck around a commander from the collection, manually filling gaps

### Later milestones (designed-for, not built)

- **Intermediate:** import existing decks (Moxfield), win/loss tracking, per-game strength/weakness notes, cross-checking recommendations against cards committed to existing decks
- **Advanced:** LLM-powered (Claude API) card suggestions for incomplete decks and tuning advice derived from win/loss notes

The recommendation engine is hybrid by design: deterministic heuristics for scoring (v1), LLM reserved for fuzzy tasks (later milestones).

## Architecture

A single Next.js app (App Router, TypeScript) deployed on Vercel (Hobby tier), with Neon Postgres (free tier) via Drizzle ORM. Auth via Clerk (free tier). No monorepo.

Three logical layers:

1. **Web UI** — pages for Collection, Commander Recommendations, Deck Builder.
2. **API routes / server actions** — CSV upload & parsing, recommendation queries, deck CRUD.
3. **Data jobs**
   - **Scryfall seed job:** downloads Scryfall's free "oracle cards" bulk data (~35k unique cards) into Postgres. Idempotent (upsert by `oracle_id`). Run manually or via weekly Vercel cron to pick up new sets.
   - **EDHREC fetcher:** pulls per-commander synergy JSON from EDHREC's endpoints on demand, cached in Postgres with a 30-day TTL. EDHREC endpoints are unofficial — cache aggressively, degrade gracefully (see Error Handling).

**Cost:** $0/month plus a domain the user already owns (`the99.<domain>`).

### Rejected alternatives

- **Live Scryfall API (no local card DB):** collection-wide analysis would mean thousands of rate-limited API calls per recommendation run. Too slow for the core feature.
- **LLM-centric pipeline:** per-call cost scales with collection size, hallucination risk on card facts, unexplainable results. LLM kept for later fuzzy tasks only.
- **Render hosting:** ~$7/month or free with cold starts; Vercel + Neon is $0 with none.

## Data Model

Users live in Clerk; all user-scoped tables carry a Clerk `user_id`.

| Table | Purpose | Key columns |
|---|---|---|
| `cards` | Scryfall oracle catalog (~35k rows) | `oracle_id` (PK), name, mana cost, CMC, color identity, type line, oracle text, keywords, commander legality, image URI, rarity |
| `collection_items` | Owned cards | `user_id`, `oracle_id` → cards, quantity, ManaBox pass-through (set, foil, condition) |
| `decks` | User decks | `user_id`, name, `commander_oracle_id`, status (`brewing` / `built`), notes |
| `deck_cards` | Cards in a deck | `deck_id`, `oracle_id`, quantity. Ownership is not stored: the deck view derives each card's owned/unowned status from `collection_items` at read time |
| `edhrec_cache` | Cached EDHREC payloads | `commander_oracle_id`, JSON payload (top cards + synergy scores), `fetched_at` |
| `csv_uploads` | Upload log | `user_id`, filename, row count, unmatched count, unmatched rows as JSON, timestamp |

## CSV Upload & Matching

1. User uploads a ManaBox CSV export.
2. Server-side parse; each row matched to `cards` by Scryfall ID (ManaBox includes one), falling back to exact name match.
3. Result summary shown before commit: "1,842 cards matched, 3 unmatched," with unmatched rows listed. Unmatched rows are logged in `csv_uploads`, never silently dropped.
4. On confirm, the user's collection is **fully replaced** (not merged). ManaBox exports the whole collection each time, so full-replace keeps state consistent. The confirmation step shows the diff count against the current collection.

## Commander Recommendation Engine

Two stages, fully explainable:

**Stage 1 — candidates.** Query the collection for every card that can legally be a commander: legendary creatures plus cards with "can be your commander" text.

**Stage 2 — viability scoring.** For each candidate:

- **Color identity pool** — count of owned cards legal in the commander's color identity.
- **EDHREC overlap** — the strongest signal: how many of the commander's top ~100 EDHREC-recommended cards the user owns (fetched via the cache).
- **Curve & role coverage** — does the color-legal pool hit target counts per role? Roles bucketed by keyword/type heuristics: ramp (10+), card draw (10+), removal (8+), lands.

**Results page:** ranked commanders, each with a breakdown, e.g. *"You own 41 of EDHREC's top 100 cards for Muldrotha. Color pool: 312 cards. Ramp ✓ Draw ✓ Removal: thin (6)."* Clicking a commander opens the Deck Builder seeded with it.

If EDHREC is unreachable and no cache exists, scoring degrades to color pool + role coverage, and the UI says so.

## Deck Builder

Workspace for assembling the 99 around a chosen commander (from recommendations or search):

- **Suggested list** — pre-populated from owned cards: EDHREC top cards the user owns, then role-based fills (ramp/draw/removal/lands) from the color-legal pool. Suggestions only; nothing is committed until added.
- **Manual control** — search the full collection filtered to color identity; add/remove anything. Live role counters (ramp/draw/removal/land counts) show gaps.
- **Gap tracking** — deck view distinguishes owned vs. unowned slots. Users may add any legal card (including unowned ones, via full card search); unowned cards are flagged — this is the shopping list.
- **Export** — copy-as-text in standard decklist format (pasteable into Moxfield or a buylist).

## Error Handling

- Unmatched CSV rows: surfaced in the upload summary and stored in `csv_uploads`; never silently dropped.
- EDHREC failures: serve stale cache if present; otherwise degrade to Scryfall-only scoring with a visible notice.
- Scryfall seed job: idempotent upserts; a failed run leaves the previous catalog intact.

## Testing

- **Vitest** unit tests for the pure logic: scoring engine, CSV parser, role-bucketing heuristics.
- **Fixtures:** a sample ManaBox CSV and canned EDHREC payloads — tests never hit the network.
- **UI:** verified manually in the browser (golden path + edge cases) before any feature is called done.

## Deployment

- GitHub repo → Vercel auto-deploy on `main`.
- Neon Postgres; optional Neon branch for a dev database.
- Weekly Vercel cron triggers the Scryfall refresh.
- Hosted at `the99.<owned domain>`.

## Branding

- **Name:** The 99 (the 99 cards behind every commander).
- **Tagline:** "99 problems, but your commander ain't one."
- Visual identity (palette, typography, icon) is being explored in a parallel Claude Design discovery round; its output will baseline the UI work. Constraint: evoke MTG adjacency without copying Wizards of the Coast trade dress (no mana symbols, no card-frame imitations).
