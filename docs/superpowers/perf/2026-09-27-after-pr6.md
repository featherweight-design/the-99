# What is left after the performance lane's PRs 1–6

Written for Hugh, to decide which parts of #687 (the navigation-performance design, nine PRs)
are still worth building. It measures what the performance lane left on each of his four targets
and on the other main routes, then goes through #687 PR by PR against that remainder.

**Short answer.** Two slow things remain, and #687 is not the cheapest way to fix either:

1. **The deck page** still spends about 0.9s on the server, on every visit. That is #687's PR 8,
   and it is worth doing, as a query-time PR on its own.
2. **Every client navigation waits at least ~300ms**, even when the server answers in 40ms. That
   is React holding the route's loading screen on screen for its 300ms minimum. #687's cache and
   prefetch work (PRs 2–6) would remove it, but a much smaller change could too. That smaller
   change is a design call: whether a fast route should show its loading screen at all.

Home, `/decks`, `/discover` and the card details press are now under ~120ms warm. `/collection`
(~400–440ms) and `/commanders` (~360ms) sit between, for different reasons. `/collection` spends
most of its time streaming: its server finishes at ~360–390ms against a ~65ms first byte, which is
what #687's PR 7 (payload composition) would work on. `/commanders` finishes streaming at ~100ms
and spends the rest rendering a large list on the client, which none of #687 addresses. #687's PRs 2–6 and 9 would buy little beyond the 216–226ms navigation floor, at the
cost of adopting Cache Components and a client invalidation story on every converted route.

## How it was measured

- **What:** `next start` of the performance lane's PR 6 branch (#1079), which is main at
  #1076 and #1078 plus PR 6. The control rows are `origin/main` at #1080.
- **Where:** a scratch Neon branch holding a `pull:staging` copy of the reference account: 19 decks
  and 3,250 collection rows. The deck page is the account's largest deck, 96 rows.
- **How:** `pnpm measure:load` (median of 3) for full page loads and the card press. A scratch
  script times client navigations from Home INSIDE the page, and counts each navigation's RSC
  fetches and their bytes over the wire (`transferSize`).
  - It times inside the page because `measure:load`'s own "soft" column reads about 320ms for
    every route. That figure includes Playwright's polling. The in-page figures agree for a
    different reason, found below.
- **Caveat:** these are local figures. This machine reaches the database in ~33ms; production's
  functions (iad1) reach it across the continent (us-west-2). They compare builds; they are not
  what Hugh sees.

## The navigation floor

Client navigations from Home, timed in the page from `router.push` to the first frame showing
content. Revisit means the second visit in the same tab.

| Route | 1300 first | 1300 revisit | 390 first | 390 revisit | RSC fetches per navigation |
|---|---|---|---|---|---|
| Home | 310 | 312 | 308 | 311 | 1 |
| `/decks` | 339 | 315 | 337 | 318 | 1 |
| `/decks/[id]` | 967 | 902 | 961 | 924 | 1 |
| `/collection` | 343 | 323 | 557 | 320 | 1 |
| `/commanders` | 312 | 319 | 317 | 312 | 1 |
| `/discover` | 316 | 313 | 314 | 313 | 1 |

Every route but the deck page lands at 310–345ms, with one exception: `/collection`'s first visit
at 390 took 557ms. That holds whether the server takes 40ms (Home, `/decks` since PR 6) or 110ms
(`/discover`). The RSC fetch itself finishes in 41–83ms. It is not the network and not the server:

- Every route has a `loading.tsx`, so a navigation shows the route's loading screen at once.
- React then keeps a shown Suspense fallback on screen for at least `FALLBACK_THROTTLE_MS = 300`
  (in Next's bundled `react-dom`), so content cannot replace it sooner.

**It was checked by removing every `loading.tsx`** from a local build of main (not committed) and
re-timing:

| Route | with loading screens (revisit) | without (revisit) |
|---|---|---|
| `/commanders` | 317 / 318 | 98 / 93 |
| `/discover` | 315 / 312 | 99 / 86 |
| `/collection` | 337 / 334 | 302 / 322 |
| `/decks/[id]` | 886 / 833 | 813 / 805 |

Each cell is 1300 / 390. That build predates PR 6, so Home and `/decks` were still slow on its
server and are left out. With PR 6's ~40ms server they would behave like `/discover`.

So on every route whose server is fast, the loading screen costs about **216–226ms per
navigation**. On `/collection` and the deck page the server and render dominate, and the screen
costs little.

## #687, PR by PR, against that remainder

#687's success criteria are "a warm revisit costs 0 RSC fetches", a smaller `/collection` payload,
and a faster deck page. Each revisit above costs 1 fetch, as #687 measured. What that fetch costs
is now the question:

| Route | Payload per navigation (over the wire) |
|---|---|
| Home | 11 KB |
| `/decks` | 5 KB |
| `/decks/[id]` | 22 KB |
| `/commanders` | 49 KB |
| `/collection` | 289 KB |
| `/discover` | 357 KB |

| #687 PR | What it buys now | Verdict |
|---|---|---|
| 1. Probe and baseline | The lane's PR 1 (`measure:load`, `load-history.md`) already records before/after at both widths. What remains is the zero-fetch probe, which only matters if 2–6 happen. | **Drop**, or fold into whichever PR needs it. |

The client invalidation story is hardest on the deck page, where every edit, claim and pull changes it. | **Not worth it for `/decks`** (see the cheaper fix below). **Risky for the deck page**, and it doesn't touch the first visit. |

### The cheaper fix for the navigation floor (a design call, not yet built)

Removing the loading screens took navigations to fast routes from ~315ms to ~95ms: Next keeps the
current page up until the next one is ready, instead of flashing a loading screen that React must
then hold for 300ms. **The experiment removed every `loading.tsx`, the root one included, and the
root one matters:** `src/app/loading.tsx` wraps every route below it, so deleting only
`/discover`'s would leave the root boundary to show instead, and the floor with it. A route that
should skip the screen needs no boundary between it and the root layout. The cost is feedback on a cold miss: Home's first visit after a write
recomputes (~850ms locally) and would show the old page for that long.

Two ways to keep feedback without the floor, and they are Design's to choose between:

- A pending state on the link or the nav rail (`useLinkStatus`), instead of a full-page loading
  screen.
- Keep a loading screen only on the routes whose server is slow (the deck page, and `/collection`
  on a cold miss), and drop the root `loading.tsx` so the fast routes have none above them.

This is a handful of files, against #687's nine PRs, and it moves every navigation to Home,
`/decks`, `/commanders` and `/discover`.

## Recommendation

1. **Deck query time (#687 PR 8), as the next performance PR.** It is the one remaining cost users
   hit on every visit, with a span breakdown to start from.
2. **The navigation floor, through Design:** whether fast routes keep a full loading screen.
   The measured win is 216–226ms per navigation on each route whose server is fast.
3. **Stop there on #687.** Cache Components (PRs 2–6) would mainly remove that same floor on
   revisits. The two items above get most of that win without the migration or a client
   invalidation story on every route. `/collection`'s revisit (PR 3) and its payload (PR 7) are the
   parts worth revisiting later, if browsing the collection still feels slow on a phone after that.
