# About audit: which entries a player needs (2026-10-27)

Hugh, on 2026-10-27: "We have, what, 83 entries? This starts to feel like too much and I don't even know if users will find it helpful. Can we audit these entries to determine if they're all necessary or if anything can be consolidated? While I want people to know how to use the app and what everything means, they shouldn't need to read a user guide ahead of time."

This is preparation only. No code has changed and no PR is open. The rule for when a feature owes an About entry is Hugh's to decide, and this doc only proposes options for it.

## Summary

## How the launch rule could work with fewer entries

Today's rule (AGENTS.md) says no feature launches without an About entry in the same round, and a multi-round line batches its entries at the end. The Home banner announces new entries by title, up to four, then "and N more". A switched entry is announced when its switch turns on. A line inside an entry follows its switch but is never announced. The research behind the options below is in "Appendix: how About is wired".

- **Option A: group the page and keep today's entries underneath.** The Reference and the `?` panel draw each place as one entry, with each feature as a line. The code still holds a few dozen line-sized records with ids, so the banner, Tools and How it works keep working unchanged.
  - The rule becomes: "A feature adds a line to its place's entry, and the banner names that line."
  - This is the cheapest option. It reduces what the reader sees, not what the code counts.
  - It also fits poorly with the 44 cuts, since a cut fact has no line to keep.
- **Option B: area entries whose lines are the announced unit.** Each line carries its own switch and `since`, and the banner names lines (for example "Collection: Scanning your cards").
  - The rule becomes: "A feature adds or updates a line in its area's entry, and the banner announces the line."
  - It closes today's gap where a switched line is never announced.
  - It costs the most, because it reworks the seen state and the banner's tests.
  - It is the only option where the code really is one entry per area and announcements stay precise.
- **Option C: area entries announced as a whole.** An area counts as new whenever what it draws for a reader changes, and the banner names the area ("1 new in About: Your collection").
  - The rule becomes: "A feature adds or updates a line in its area, and the area is announced."
  - It is coarse. A reader learns that an area changed, not what changed, and a wording fix can re-announce an area.

**A further option, which doesn't need About at all.** With 13 drawn entries, most launches would touch no entry. The rule could instead say: "A feature launch owes an About change only when it adds a fact a player can't see on screen. Otherwise it owes its own help line, and the release banner, or a What's new line on Home, announces the launch." That separates announcing a launch from explaining it, and this audit suggests those are two different jobs.

**My recommendation, for Hugh to decide.** Option B, together with the narrower "owes an About change only when it adds a hidden fact" rule. Option B is what keeps the banner meaningful once entries are few, and the narrower rule keeps About from growing back to 83.

### 2. The release banner and versioning

### Seen state

`user_prefs` holds two columns: `about_version_seen`, a floor, and `about_seen_ids`, a text[] (migration `drizzle/0066_about_seen_ids.sql`). They are read by `aboutSeen` (`src/lib/about/read.ts:26-33`). `isSeen` (`visible.ts:192-196`) decides an entry three ways:

- An entry drawn in its variant is seen by `<id>@<SWITCH>`.
- A switched entry is seen by its id.
- An unswitched entry is seen when `since <= version`.

`unseenEntries` (`visible.ts:207-210`) returns nothing for a first-run reader (`version 0, ids []`). A visit to the Reference records the floor plus `switchedIds(visible)` as a union (`markAboutVisitedQuery`, `read.ts:40-57`), through `RecordVisit` (`page.tsx:143-155`).

### The banner (About on the banner, PR A #1780, 2190e5709)

With `ABOUT_SHEET_ENABLED` on, which it is on both projects (plan `2026-10-15-about-on-the-banner.md:153`), the proxy no longer redirects or draws the sheet (`src/proxy.ts:121-125`).

- **Who gets a line.** Home computes `aboutNotice(seen, visible, sheetCookieCurrent)` (`src/lib/about/notice.ts:25-34`, read in `src/app/page.tsx:70-74, 217-219, 297`).
  - A first-run reader gets one sentence introducing the page.
  - A reader who is behind gets the unseen entries.
  - A current reader, or a browser whose legacy `about_sheet` cookie is current, gets nothing.
- **What the line says.** `aboutLine` (`notice.ts:46-50`) hands the browser the entries' titles and their `displayedId`s.
  - The banner draws `N new in About:` and then the titles (`src/lib/copy/arrivals.ts:33-43`).
  - Four or fewer titles are named in full. Past four, it names three and "N more" (`sheetTitles`, `src/components/shell/about-sheet.tsx:14-16`; drawn at `src/components/home/arrivals-banner.tsx:91-107`).
  - Show me goes to `/about?tab=reference#new` (`arrivals-banner.tsx:35-37`).
- **The ✕.** It writes seen through `aboutDismissal` (`notice.ts:67-97`). That function re-derives the notice on the server, honors only the claimed ids it still names, writes switched and variant ids, and raises the floor no higher than the oldest unclaimed unswitched entry's `since - 1`. Claims are capped at `MAX_CLAIMED = 200` (`notice.ts:53`).
- **Reach.** The banner appears on Home only (Q1, plan :10). Every other page shows nothing.

**The banner's unit is the entry, by title and id.** It cannot name a line, and nothing it does is keyed below the entry, except a `variant`, which counts as a separate unit (`<id>@<SWITCH>`).

### What a switched entry does to the banner

A switched entry bumps nothing. Its `since` is simply the version current when it ships (`about.ts:77-83`; for example `start-without-a-collection` at `about-entries.ts:94-97`).

It is announced when its switch turns on for a reader. That can be a deploy or a `flag_overrides` change, and it needs no code change: the entry becomes visible, its id is not in `about_seen_ids`, so it counts as unseen. The test "reads unseen when switched on after another was switched on and read (out of order)" pins this (`visible.test.ts:229`).

For the same reason, `since` cannot work for switched entries (`visible.ts:188-191`), because switches flip in any order.

### What `since` does on a merge

The guard is the content hash in `src/lib/copy/about.version.json` (`{"version": 16, "hash": "bb2c…"}`), checked in `src/lib/copy/about.test.ts:82-105`. It hashes every visible string of `aboutEntries`, `aboutCopy`, `aboutMenuCopy` and `aboutSheetCopy`. Any copy change therefore forces one of two things:

- a bump of `ABOUT_VERSION`, which announces to readers; or
- a re-pin of the hash, which is silent.

If entries are merged, whether readers are told depends entirely on two choices: whether the new entry carries a `switch`, and what `since` it gets.

- **An unswitched merged entry with `since <= 16` is silent.** A current reader's floor is 16, so it counts as seen. A reader whose floor is below the `since` is told. So `since` set to the minimum of the merged entries (for example 1) announces to nobody. That is also the honest value under rule 5, where `since` is the version the entry first appeared in.
- **An unswitched merged entry with `since: 17` and a bump announces to everyone.** Every reader at 16 is told every area as "new", for example "9 new in About: Your collection, Building a deck, Tuning, and 6 more." The Reference's what's-new index lists them all.
- **A merged entry that keeps a switch is seen by its id.** If the id is new, it is new to every reader who has that switch on, whatever `since` says. Keeping an old id keeps the old seen state.
- **Folded lines lose their announcement.** Once former switched entries become `captionLineSwitches`/`keySwitches` lines of an unswitched area entry, they are never announced again, because lines have no seen state (§1). That is the real mechanical loss. Seven of the 43 switched entries are currently off in production per AGENTS.md: friend decks, spare requests, push, near combos, strategy focus, the Commanders place and upcoming precons. When Hugh flips one of those later, nothing would reach the banner.
- **Old ids left in `about_seen_ids` are inert.** Nothing reads an id that no entry holds, so no migration is needed for them.

The test suite also pins the version history:

- `visible.test.ts:103-105` expects the newest unswitched `since` to be exactly 16, held only by `about-rebuilt`.
- `about.test.ts:107-112` refuses a `since` above `ABOUT_VERSION`.
- `visible.test.ts:31-133` holds that, with every switch off, the model reproduces the legacy version rule at every seen level.

Any merge edits these deliberately. One more constraint: the comment at `about.ts:77-83` forbids reusing 15.

### 5. What a merge or cut costs mechanically

**Free (dead weight to delete):** `chapter`, `width` and `marksPending` on every entry, and the `[data-marks-pending]` CSS rule. No renderer reads any of them (§1). The per-entry specimens and numbered marks are already gone, so no figure is orphaned in code. The design artboards for the old specimens are reference material and orphan nothing either.

**Per-entry assets that a merge orphans or forces to be redone:**

- **Halo boxes.** There are 83 locator keys (`about-locators.mjs`) and 83 × 6 themes of boxes in `shots.generated.ts`. An area entry gets one halo per frame, so the "this control" pointer is lost for every folded line. Alternatively, halos become per line (a new data shape and a capture change). The screen frames themselves (`REQUIRED_SHOTS`, `shots.ts:35-40`) are per screen and survive any merge that keeps screens.
- **The help panel's per-screen mapping.** An entry has exactly one `screen` and, on a deck, one `view` (`about.ts:192-195`, pinned by `about.test.ts:183-196`). An "area" spanning Collection, card details and Upload, or several deck views, would show on one place's ? only, unless areas are one per place. `about.test.ts:192-196` also requires every one of the 23 places to have an entry. So "one per area" with fewer than 23 areas means either dropping places from `ABOUT_SCREENS`/`DECK_VIEWS` (which also touches the 23 required shots and `reference.test.ts:27`) or letting an entry name several places.
