## 1. #140 — refusals under a deck row

### 1.1 Placement → **inline, under the control that was clicked. Ratified, and the toast is refused.**

Not a preference. Three shipped facts decide it:

- **This app has no toast pattern**, and the bottom of a phone viewport is already spoken for —
  route dock at `bottom: 80px` over a fixed 80px tab bar (`ADDENDUM-README.md` decision 1). A
  toast would fight the dock or float over the tab bar.
- **`MutationError` already renders in place** under the acting control, and every state doc in
  the project reaches for it: the log form's `Save refused` (`design_handoff_the99_game_log/
  README.md`), keep-all's refusal under the cluster (`STATES-keep-all-auto.md` state 5), the
  refused undo inside the row (`ADDENDUM-README.md` decision 5).
- **A refusal is the answer to a press.** It belongs at the press, not at the edge of the screen,
  and it must not outlive it.

So: **inline, under the pressed control; form state and row state preserved; no toast, no timer,
no live-region announcement for the refusal itself.** A refusal in one control never disables a
sibling control (`design_handoff_the99_synergy_discovery/STATES-fill-controls.md` rule 5).

### 1.2 The deck-full string → **stays deleted. Ratified — and confirmed already gone from main.**

2026-09-07: eng confirms `DeckAddRejection` is a three-member union, the cap string is gone, and
no test asserts on it. Nothing to do; the paragraph below records why it stays gone.

assertions (`mutation-result.test.ts`, `add-validation.test.ts:66`) — **deleted, not reworded**
(`design_handoff_the99_over_99/README.md`, `over-99 · copy strings.ts` REPLACES block). A deck may
pass 99 and reads `Over`; adding at 104 succeeds, and the singleton and colour-identity rules are

### 1.3 The remove-path fallback → **new string, and it names what is still true.**

## 2. #148 — the 99/99 reveal

**All four calls ratified.** Three of them are the shipped shape; the fourth is a deletion.

**1 · A band, not a full surface. Yes.** The reveal fires on a status flip the player performed —
the last add, or a hand-trim from 104 to 99 (`design_handoff_the99_over_99/README.md` decision
10). A full surface interrupts an editing session that has not ended and has to be navigated out
of; 99 is not a terminal state in this product, since building long and trimming back is a
documented normal path. The over-99 pass already records the reveal as a **shipped band** (README
state table, C2). Band is not a downgrade; it is the correct register for a receipt.

**2 · Dismissible only, no auto-timer. Yes.** Same argument as #185's undo row: *"a 5-second
toast that also vanishes fixes half of it"* (`ADDENDUM-README.md` decision 5). A thing that
removes itself cannot be caught by a player who looked away at the moment they earned it. It is
cleared by the dismiss control or by leaving the route — nothing else, and no timer.

**3 · A derived mobile composition, not a drawn one. Yes.** The band reflows: stacked
composition, full-bleed within the reserve, dismiss at a 44px target, illustration pays first if
the composition is tight (`ADDENDUM-README.md` decision 2). **No separately-drawn mobile reveal**
— #158's locked parity constraint forbids width-only constructs, and a second drawing is how one
gets built by accident.

**4 · `commandersCopy.firstRun.directive` → re-run, 2026-09-07. My first pass was wrong on the
facts. Keep the key; reword.**

Withdrawn: the cross-route-borrow and duplicate-directive arguments both fail. The string renders
in `GuidedBanner` on `/commanders`, gated on zero decks (`commanders-view.tsx:258`,
`commanders/page.tsx:216`) — it is a commanders-route string in the commanders copy object, which
is correct. And the reveal body I quoted lives on `/decks/[id]` at build 99, which a first-run
user has by definition never reached. **The two never co-occur.** Cutting the key would leave
guided-setup step 2 of 3 with nothing to act on.

Current text — *"Pick one to build your first 99."* — judged as a first-run banner directive:

**One change. Name the noun:**

```
"Pick a commander to build your first 99."
```

*"Pick one"* is an anaphor with no antecedent inside its own banner. It resolves only if the
reader has already parsed the grid behind it as *commanders* — which is precisely what a first-run
user has not done yet, and this is the one string whose whole job is to tell them. Everything else
is right and stays: second person, one clause, one action, no numeral gloss (§3.3 does not bite —
*"your first 99"* is the deck-size sense and the only sense on screen), and it survives being read
as step 2 of 3 without knowing steps 1 or 3.

## 3. #182 — six calls, four divergences

### 3.1 The unconditional pluralisation → **ratified as-is. The rule already ships — see §6.2.**

Rule, not a one-off: **any string with an interpolated count carries both forms in the copy file,
and never `(s)`.** Precedent is committed — `STATES-over-99.md` state `built === 100` is singular
throughout (`+1`, `1 to cut`, *"One over the ninety-nine"*) and the copy file carries both forms,

### 3.2 The worked example → **reword. Ruled at §6.3** — the width premise was wrong; the defect

Ninety-nine is the deck size, the progress denominator, and the product's name. All three are

that has no jokes in it. **Keep the gloss in the one place the question arises** — the spine's
progress figure, where the number is on screen as a denominator. The other two strings drop the
gloss and keep their own facts. This is the same reduction as the empty caption's doubled
*"ninety-nine"*: the first one means something (`ADDENDUM-README.md` §8).

## 4. #242 — table 15.10, FilterPanel option list

**Plain yes. Amend the table; nothing on screen changes.** This restates and does not reopen
R4 §6.

**Table 15.10, row *FilterPanel option list*** — replace `checkbox group` with:

> **Multi-select listbox.** `role="listbox"` with `aria-multiselectable="true"`; `aria-selected`
> on every option; no exclusivity. Each option's accessible name carries its count (*"In use, 61
> cards"*). **Zero-count options stay `aria-disabled`, not removed.** Checkbox visuals may stay if
> they already ship — the role is the amendment, not the pixels.

What the table was protecting was *more than one at a time*, and `aria-multiselectable` protects
it. The search field is the load-bearing part: ~14 options with counts is exactly where search
stops being optional, and WAI-ARIA 1.2 gives a `role="combobox"` with `aria-activedescendant` no
variant that owns a checkbox group. **Do not redraw the search affordance** — that alternative
trades a correct, shipped control for a table's shorthand. `Sort ▾` remains deliberately outside
this row.

## 5. Availability marker placement (unfiled)

**Plain yes. Build accepted; §3.1's placement sentence is the stale half.** This restates and does
not reopen R4 §5.

**Design table §3.1, decklist row** — amend the placement sentence only:

> The marker draws **inline in the name cell**, between the card name and the buy tag. It does not
> attach to a `×N owned` string, and there is no shared meta line.

§3.1 appended the marker to `×N owned` on a shared meta line; **the shipped decklist row draws
neither**, so the table was describing a row that does not exist. The build did not deviate — it
found a stale spec. The `×N owned` host was chosen so the marker could ride an existing string
rather than claim a column; the name cell does the same job with the same slack the collection row
borrows.

**§3.1's hard constraints stand unedited** — no new grid column, 34px / 44px row height. Two
things to pin while amending:

- **The name yields, the marker doesn't.** Marker is `flex: none`, name truncates. A clipped name
  beside a legible marker beats the reverse, as on collection.
- **Marker before the buy tag, always.** The buy tag is an action; the marker is a fact about the
  card. Fact then action, left to right, and the tag keeps the row's right edge.

Nothing on screen changes.

### 6.1 · #140's four surviving refusals → **ratified as-is. Ship unchanged.**

```
:14  "We couldn't add that card just now. Give it another try in a moment."
:19  "This card isn't legal in Commander, so it can't join the deck."
:20  "This card's colors sit outside your commander's color identity."
:21  "This card is already leading the deck as its commander."
```

Each passes the test I set. `:19`–`:21` state the durable fact about the card and let the refusal
follow from it, rather than reporting a failure — and `:21` is the best of the four, because
*"already leading the deck"* is information the player can act on. `:14` is the only transient one
and correctly the only one that invites a retry. No apology chain, no *"unchanged"*, no
numeral-only clause. Correct: none names a deck, so R5 §8's count-only sibling rule does not bite.

One note for whoever edits this file next, not a change: `:14` is the one string that must keep
*"just now"*. It is what separates a transient failure from the three permanent ones, and it is
the difference between a retry and a dead end.

### 6.2 · #182's pluralisation → **released. Ratified as-is; the rule already ships.**

`plural(n, one, many)` at `decks-builder.ts:37`, every count string branching through it, no `(s)`
form anywhere. §3.1's rule is a description of shipped code, not a request. Nothing to file.

### 6.3 · #182's worked example → **reword. Premise corrected: this was never about widths.**

My §3.2 reasoned from column constraint; the callout is a desktop-only full-width flex row
(`role-counter-strip.tsx:123-146`) and never overflowed. The real defect is at `mix.ts:84-87` and
is worse than a fit problem: **the string prints a figure about a deck it cannot read.** On an
empty deck it renders *"A deck sitting at 8 is fine"* directly under a RAMP cell reading `0`. The
callout is a static explainer sitting beside a live counter, and the moment it names a number it
looks like it is naming *yours*.

```
"Ramp · rec 10. Decks that cast a 4-mana commander on curve average ~10 sources. Fewer is a slower build, not a broken one."
```

The reassurance was the good part of the old ending and it survives — what goes is the invented
figure. `rec 10` and `~10` are claims about Commander decks in general, which this string is
entitled to make; `8` was a claim about the reader's, which it is not. Rule for the rest of the
strip: **an explainer string may cite the recommendation, never a current value.** Live values
belong in the cells, which can read them.
