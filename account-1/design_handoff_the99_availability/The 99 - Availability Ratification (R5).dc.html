Item 11's follow-up · the drawing call rows-view.tsx:72, :79

Both coexist — and the outset ring needs no four-plus switch

Keep the inset edge exactly as it ships, add the outset ring unconditionally. They answer different questions, and the second one answers itself: an outset ring painted in the row's own background is invisible when there is nothing underneath it. At one to three pips it paints row colour onto row colour — a no-op, pixel-identical to today. At four and five it is the only thing between two overlapping circles. So there is no state to gate: the pip never learns how many siblings it has, and a conditional shadow — the tempting version — would make a primitive count its neighbours to decide how to look.
The two jobs, stated plainly: inset 0 0 0 1px rgba(0,0,0,0.35) defines a pip against the row — it exists because --w is #F4E9C4 and needs a rim on a dark surface. The outset ring defines a pip against the pip under it. Neither substitutes: drop the inset and white loses its rim at every count; use only the inset and five overlapping circles merge into one dark-veined blob.

The spec, added to item 11
Shadow, every pip, every count:
0 0 0 1px var(--pip-ring),
inset 0 0 0 1px rgba(0,0,0,0.35)
Order matters: outset first. The inset edge must stay the innermost line — it is the pip's own rim, not a divider.
The one piece of plumbing: --pip-ring on the row element, --surface at rest and --elevated-hover on hover — the row already swaps that background, so the ring rides the swap it already makes. Hard-coding --surface leaves a visible hairline on hover at four-plus pips; that is the only way to get this wrong.
Scope: the two inline spans in rows-view.tsx only. ColorPip is untouched — its outset slot is spoken for by the 2px var(--accent) selected ring, it never overlaps, and it is a control rather than a readout.
Cost: the visible fill of a covered pip is a ~6px crescent minus 1px of rim. Checked at five pips, both widths — still reads as five colours, in order.
§ Resolved engineering-side — ratifications

Six items, and the three sentences that change

Item 1 Behaviour ratified; §6's sentence is what's wrong ratify + reword
The worked table is right and the implementation is right: a deck's own copies count for neither side of the sum. Claims-exclusion alone renders Arcane Signet as 0 free — in Kykar inside Atraxa, which is the exact sentence §6 exists to prevent. Supply-and-claims exclusion is not a stronger version of the rule; it is the rule, because “this card is built with, here” removes the copy from both roles at once.
Replace §6's rule sentence with: Inside a deck's own list, that deck's copies count for neither side of the sum — not as supply, not as a claim. Then the formula, so nobody re-derives it: free = (owned − ownClaim) − (hard − ownHardClaim).
And the withdrawn flag is correctly withdrawn — with a reading worth keeping: from a self-excluded vantage, free === 0 means exactly enough for everyone, including this deck. So none free inside a deck's own list isn't merely unreachable, it would be false. That is a stronger guarantee than “the state doesn't occur” and it should be the note in the code, not the prose about noise.

Item 5 Add-panel exclusion ratified — and here is the seam, stated once ratify + generalise
Right call, and §6 was under-scoped rather than the panel over-reaching. “A deck's own decklist” named a surface; the reason it gave named a vantage point — inside a list, the card is built with. The panel is where you add to that list, so the vantage is identical and the same card one panel apart cannot answer twice.
So don't relocate the seam — name it, so the next surface costs no round: The vantage point is the deck you are editing, not the surface you are looking at. Anything mounted inside a deck route excludes that deck; anything outside it computes against everything. That covers the decklist, the panel, a card modal opened from the builder and whatever the builder grows next, and it leaves /collection and /commanders exactly as #43 drew them.
