Item 11 · the drawing call /collection row · pip track · predates availability

The track holds. The pips shingle.

Not a wider track, not a wrap, not a +2. Pips overlap by 45% of their own width once there are four or more of them — a shingle, like a fanned hand — and every colour stays visible inside the shipped track at both widths. Widening moves a grid the last two passes went out of their way not to move, for the rarest row in the list. Wrapping breaks constant row height, which is the whole argument for the marker being inline. And an overflow token would hide colour identity, which is the one thing this cell exists to say.
The reason a cap isn't needed: five is the ceiling. Colour identity cannot exceed WUBRG, so unlike a deck name this overflow has a known worst case — you can solve it exactly once and never write a truncation rule. One to three pips render pixel-for-pixel as they ship today; the shingle only engages where the row was already broken.

The spec
Track: unchanged — 38px 40px 1fr auto and 52px 54px 1fr 150px 92px 18px ship as-is. No column widens, none is added.
Pip: 11px phone / 13px desktop, unchanged.
Step: 14px / 17px for 1–3 pips (today's gap), 6px / 8px for 4–5 — i.e. margin-left:-5px at both widths.
Order & z: WUBRG left to right, z descending so each pip's left edge sits above its neighbour. The overlap reads as a stack, not a smear.
Ring: 0 0 0 1px in the row's own background token — --surface, or --elevated-hover on hover. Not a new token, and load-bearing: --b is #1E1B1A against a #1E1A15 surface — without the ring, black beside black is one shape.
Row height: 34px / 44px, untouched. This is a horizontal fix only.
Accessibility: unchanged — the pips stay aria-hidden decoration; colour identity is already spoken by the row label. Overlap is not information, so nothing new to announce.
Worth saying out loud: this bug is older than #43 and the sweep only found it because five-colour cards are a handful of rows in 1,418. It is also the third thing in this feature's history to be solved by taking space that already exists rather than asking for more — the marker borrowing 1fr, the deck name dropping on collection, and now the pips fanning. If a fourth one shows up, the pattern is the answer.
Items 8 & 9 · wording ratified as taken — no new form

“none free” and “also in” are right, and they're right for different reasons

Item 8 — ratified, both halves. none free beats 0 free because the marker is read, not counted: on a decklist row it lands as ×1 owned · 0 free, two numerals a bullet apart, and the eye tries to do arithmetic on them. A word beside a numeral parses as a sentence; a numeral beside a numeral parses as a table. It also matches the soft state, which was always word-first (1 in a brew is a count that needs to be a count), and it makes the visual string and the aria string finally agree — the ear already heard “no free copies”.
The over clause unifying on also in — ratified, and it retires decks want it everywhere. Two phrasings for one state was the drift risk flagged in R1. Want also personifies a list, which is exactly the overclaim the copy file's own header bans: also in describes a list's contents, wants it gives it an appetite.
But hard keeps plain in, and that asymmetry is deliberate — don't let a future sweep “fix” it. Hard's clause says where the copies went (none free — in Atraxa); over's clause says who else is holding one from where you're standing (short 1 — also in Kykar). also is only true when there's a first — the deck you're inside. On /collection, where you stand nowhere, there is no also to earn.

Post-dates the file · with item 2 degraded read · counts, no names

One new key, and a symmetry rule so this can't happen a third time

Correct diagnosis, and the fix is the same shape as item 2's. Every *Aria key in the over family takes a deck count or a deck name; a read that returns how short but not how many lists has nowhere to put the number, so the caller falls back to a key that drops it — and the shortfall, the only fact the marker actually has, goes unspoken. Silence is the default for a free card, never for a degraded one.
Add to the shipped copy block
// Counts only — no deck name, no deck count. For a degraded read
// that resolves the shortfall but not the claimants. Describes lists.
overAriaCountOnly: (shortBy: number) =>
shortBy === 1
? 'one copy short for the lists that include it'
: `${shortBy} copies short for the lists that include it`,
Name it to match item 2's. If the count-only hard key shipped as hardAriaCountOnly, this is overAriaCountOnly; if it shipped as hardAriaNoDeck, use that suffix instead. The pair matters more than either name — the next person to add a state will copy whichever pattern is visible.
“For the lists that include it” asserts nothing about location and counts nothing it can't see — it says the shortfall is real without naming a claimant. The visual string stays marker.over (short 1), which never needed names.
Which key fires, by what the read returns
Full read — counts + names
overAria · overAlsoInAria
Counts, no names — deck count known
overAria — already count-only, unchanged
Shortfall only — no claimants at all
overAriaCountOnly — new
No read — availability unavailable
nothing; marker absent, fails quiet per R2
The rule this establishes, so the sweep ends here: every marker state that names a deck needs a sibling that doesn't. Three states name decks (hard, hard-multi, over) and a degraded read can strip the name from any of them, so the count-only variant is part of the state, not a fallback bolted on later. That is one line in the copy file's header and it is the durable half of this answer.
Two placement calls both accepted · both amend a table, not a screen

The table was wrong about the row, and wrong about the role

Design table §3.1 — the decklist row
Inline between name and buy tag — accepted, and §3.1 is the thing that's wrong
§3.1 appends the marker to ×N owned on a shared meta line. The shipped row draws neither, so the table was describing a row that doesn't exist — the build didn't deviate, it found a stale spec. The ×N owned host was chosen because it let the marker ride an existing string rather than claim a column; the name cell does the same job, and it's the same slack the collection row borrows in addendum 2. One reduction, two surfaces, same reasoning.
Constraints hold as written: no new grid column, 34px / 44px row height. Two things to pin while amending:
The name yields, the marker doesn't. Marker is flex:none, name truncates — a clipped name beside a legible marker beats the reverse, same as collection.
Marker before the buy tag, always. The buy tag is an action; the marker is a fact about the card. Fact then action, left to right, and the tag keeps the row's right edge.
Amend §3.1's placement sentence and its hard constraints stand unedited. Nothing on screen changes.
#242 · table 15.10 — FilterPanel options
Amend 15.10 to listbox — eng is right and the table is over-specified
A role="combobox" search field owns a listbox popup; ARIA 1.2 doesn't offer a variant where it owns a checkbox group. The panel's search field is the load-bearing part — ~14 options with counts is exactly where search stops being optional — so the role follows from a decision already shipped and correct.
What 15.10 was actually protecting was multi-select, and aria-multiselectable protects it. The word “checkbox” in the table was shorthand for “more than one at a time”, which is why Sort ▾ is deliberately not this panel. Amend the row to name the behaviour instead of the widget: multi-select, aria-multiselectable="true", selected state on each option, no exclusivity.
Two things I'd keep in the amended row, because they're what a reader will check: the option's accessible name still carries its count (“In use, 61 cards”), and zero-count options stay aria-disabled, not removed — a menu that changes length between players is worse than one with dim rows. Checkbox visuals may stay if they already ship; the role is the amendment, not the pixels.
