Open with Hugh · how we know a player installed

Recommendation: A, a server flag. The installed app stamps installedAt on its first signed-in open, and every browser session of that account stops asking (the row and the header slot). B (a local ✕ only) costs nothing, but it keeps asking an installed player in every Safari tab a friend's link opens. That means every invite and spare request sent over Messages.

Calls

  1. A checklist row, not a tour stop. The tour lights parts of the page to explain them. Installing means leaving the browser for the Share menu, and doing that in the middle of the tour's overlay would strand the tour. Welcome and the About line are banners. A Home card after the first deck comes too late, because by then the player has done the first visit in a tab. The row is live from the first visit, like Add your friends.
  2. Under step 3, above the signature, Friends and news rows. It's the one row that changes where the rest of the visit happens, so it leads the unnumbered rows. It has no number, so it isn't a step on the path to a first recommendation.
  3. The row. It's the Friends row's live box (radius 14, 56px floor, --surface-inset on --border-strong), with the header slot's install glyph in the numerals' 22px slot, title Install The 99 (the slot's own name) and a browser line. There are two presses, like the header slot: the row and a bare ✕.
  4. One ask at a time. While the row is on screen, the header's Install slot is hidden. The row's ✕ removes the row for good. It also counts as one header-slot dismiss (dismissOnce), so the slot stays quiet for 30 days, comes back once, and a second ✕ retires it, as shipped. The player keeps a way back without being asked twice in one visit.
  5. Copy by browser. Safari's line mentions the alerts the player chooses, because push from a Safari install is sure. Chrome, Firefox and Android don't mention alerts. The sheet itself is shipped and unchanged.
  6. How we know they installed: option A, a server flag (recommended, yours to call). The flag is set the first time the installed app opens while signed in. It hides the row and the header slot in every browser session of that account. With option B (a local ✕ only), an installed player keeps being asked whenever a link opens in Safari, and friend invites and spare-request links arrive exactly that way, from Messages. The cost is one nullable column and one idempotent write. The first launch draws nothing: no toast, no moment.
  7. No About entry (the brief's default).

Gaps for engineering

  • G1 · installedAt. A nullable timestamp on user_prefs. A client effect in the shell calls a server action once, when isStandalone() is true and the reader is signed in and has no stamp yet. The write is idempotent (coalesce).
  • G2 · One decision for row and slot. A shared useInstallAsk() hook (browser, held prompt, dismissal, standalone, installed from the server) so the row and the slot never disagree. The slot hides while the row is mounted.
  • G3 · iOS storage. The installed app keeps its own sign-in, separate from Safari, so the player signs in once more on the first launch. Hugh's call: should the sheet say so? It's left out of this round's copy.
  • G4 · Android decline. After userChoice returns dismissed, the row goes for the visit. Nothing is stored, because Chrome itself decides when to offer the prompt again.
